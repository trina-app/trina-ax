# Changelog

Published artifacts and authoritative release notes are in [GitHub Releases](https://github.com/trina-app/trina-ax/releases).
This file summarizes user-visible changes; it is not a list of every commit.

## Unreleased

- External services, requests to members: a name with only control or invisible characters is now refused, under the name field. Before, such a request was saved and showed with no name in the list and in the member's notice. In all five languages.
- Office Mac, Admin › Team settings › "Automatic update window": when the field is empty and a time set earlier with `teamax update time` is in use, the field now says so, with the window and its time zone. Before, the field looked empty and its hint said 03:00-05:00, which was not what ran. Nothing is written into the field. A window saved there applies instead, and the old time applies again if the field is emptied. Linux and hosted servers do not change. `GET /api/admin/office-update` has `windowSource` (`team`, `legacy` or `default`). In all five languages.
- Admin › System, update cards: the release notes are small text now, the same size as the rest of the card. Before, they showed at the size of a chat answer.
- Office Mac, the "new version" banner: it now shows the team's update window and time zone, for example "03:00-05:00 (Asia/Seoul)", the same as the update card. Before, it said "tonight at 03:00" with no zone, which was wrong for a window in the daytime and for anyone in another zone. A window that never opens no longer says that the update installs by itself. In all five languages.
- Office Mac, Admin › System › automatic updates: the last check and the last update now show in the team's time zone, like the next check, and each time names its zone. Before, they were in the browser's zone with no name, so one card could mix two zones. `teamax update status` prints the last check, the last update and the Windows app the same way. In all five languages.

## 0.2.21 — 2026-11-03

[Published release and notes](https://github.com/trina-app/trina-ax/releases/tag/v0.2.21)

The tag v0.2.20 was not published: its macOS build got no runner.

**Upgrade note:** take a backup first (Admin > System > Backups > Back up now). The update needs one root update on every Linux server, because the kit has a new root file. One additive database migration; going back to 0.2.19 needs no database restore. On a server with the dev environment, run `sudo /opt/trina-ax/scripts/dev-env/build-image.sh` after the update.

- Admin > System > Plan: the plan card no longer shows memory and CPU. It shows answers at the same time, people, storage and backup days.
- AI connections: a token or key that is already connected now says where it is. Before, adding it answered only "This token or key is already connected", and an owner had to sign in as the member to find and delete a personal copy. The owner and admins now see the name of the team connection, or "<name>'s personal connection '<label>'": they hold the token they pasted. A member who adds a token that someone else on the team uses sees only "already connected on this team", never whose; their own connection is named. No part of the token or key is in the answer, not even the last 4 characters. A duplicate is still refused: one subscription's limit would be counted twice, and a copy would stay behind after the token changes.
- AI connections: "Move it to the team". When the owner adds a team connection with a token that is a member's personal connection, the dialog offers to move it. The owner types the password again. The personal connection is removed and the team connection is made in one step: there are never two copies, and if anything fails (a wrong password, the provider refuses the token) the personal connection stays as it was. The token's use this month, its last use and a provider limit it is waiting out carry over to the team connection, so one subscription is still counted once. When the team connection is for other people only, the dialog warns that the member may be left without AI. The member gets a notice if they have the app open (it says so when the team connection is not for them), and Admin › Activity log shows "Moved a personal AI connection to the team". API: `POST /api/admin/credentials` takes `moveFrom`, and its 409 has `params` (`reason: duplicate_credential`, `where`; for the owner and admins also `credentialId`, `label`, `ownerName`, `movable`). A ChatGPT sign-in that is already connected still says only "already connected", with no place and no move (not covered yet).
- Admin › Members shows "No AI" next to people who cannot use AI now: they have no personal AI connection and no team connection they may use. The rules are the ones a chat uses: subscription sharing, the groups and people a connection is for, switched off, expired, refused, the monthly block limit, and the engines that answer that person (an engine whose program is missing on the server answers nobody). A provider's limit that ends within the hour still counts, because that person only waits; a longer one (a weekly cap, a Codex plan limit until its reset) and "out of credit" or a spend limit, whatever the time, show "No AI". The owner's start checklist on the home page names these people with a link to AI connections, and stays until everyone can use AI. `GET /api/admin/users?noAi=1` has `noAi`; without the flag, or on a server that does not use managed AI connections, it is left out. In all five languages. No database migration.
- Linux servers: the install kit now has `mycel-boxd`, the root helper of the dev environment, at `root/mycel-boxd` (root-owned, like `mycel-sandbox`). The dev environment is still off by default: the file does nothing without `MYCEL_DEV_ENV=1` and the `mycel-boxd.service` unit. A hosted server gets the file and no unit. Because this is a new root file, the next release needs the root update once (`needsRoot`, and a new `rootSince` at that release): `mycel-update.timer` or `sudo mycel-ctl update` installs it.
- Linux servers with the dev environment: `mycel-ctl update` now restarts `mycel-boxd.service` when an update changes `root/mycel-boxd`, before the team server restarts, and at no other time. The restart stops the boxes that run; each starts again at its next use. A service that an administrator stopped stays stopped. If the restart fails, if boxd does not answer after it, or if boxd says that boxes are not available, the update goes on and its result says so. Do one step once: the update to the next release runs the older `mycel-ctl`, which does not know this restart, so run the new `scripts/dev-env/install-trial.sh` after it. The script sees that the service runs a program other than `root/mycel-boxd` and restarts it. Later updates need no step.
- `sudo mycel-ctl update` without `--json` now prints the update's notes, so they also reach the update timer's journal.
- Hosted teams and plan files: a team on a plan smaller than its disk now keeps to the plan's storage limit. A disk cannot shrink, so a team moved to a smaller plan (a refund, for example) kept the larger disk and could write until that disk was almost full. The plan's size is now the total in Admin › System, in diagnostics and in every write check, and the 80% notice uses it too. When the team goes over the limit, the owner and admins are told once, with the end date of a 7-day grace period. After the grace period, new saves, uploads and AI writes are refused until the use is under the limit. Read, download and delete keep working, and no data is deleted. Deleted files stay in the trash and still count, so the messages say to empty the trash. A hard limit of 2x the plan applies at all times, also during the grace period. When the use drops under the limit, or after an upgrade, writes work again with no action by an operator. Operators still see the real disk size. A full local backup counts in the use, so it now stops when the plan leaves less than 2 GB of room, as on a real disk of that size. Diagnostics show this, and a team over the limit, as a warning, not a failure. A server with no plan file does not change.
- Diagnostics: "disk size differs from the plan" now shows only when the disk is smaller than the plan, which means that a disk grow failed. A disk larger than the plan is normal after a move to a smaller plan.
- Dev environment (experiment): a box can no longer fill the server disk. The disk size of a box limits only its volume (`node_modules`, `.venv`, caches), and files in the project folder are on the server disk. The box now stops when the server disk has less than 2 GiB or 5% free, the larger of the two, and it does not start again until there is 1 GiB more than that. The people who may use the box and the admins are told why. Before each command, `box_shell` applies the same storage rule as AI writes. This is not a project quota: one project can still use all the space down to that limit.
- Dev environment (experiment), upgrade step: run `sudo /opt/trina-ax/scripts/dev-env/build-image.sh` once after this update. A box now has no `fallocate` and no ioctl of type `X`, because these calls can take all the disk space between two checks of the disk floor. Tools go on with normal writes. The update does not rebuild the profile, and a box takes the new one at its next start.
- Dev environment (experiment): long commands. `box_shell` has a new `job` mode for a render or a large build: the call returns at once and the chat does not wait. The person who started the job gets a notice with the exit code, the end of the log and a link to the chat when it ends, and the next `box_shell` call in that project gives the AI the result. The AI does not go on by itself. The project page shows running jobs with their time and last log line. Dev servers with `background` work as before, with no notice. One additive database migration (219); the schema reader level stays 4.
- Dev environment (experiment): a running render no longer stops at the idle time. A box now counts as active while it uses CPU, for at most 6 hours past the idle time, so an endless loop stops too. An idle dev server still stops.
- Hosted teams and plan files: copying a file or a folder, restoring a file version, `save_url` and connected-folder sync now respect the storage check. Before, they could write past it. A connected-folder sync that has no room leaves the file for the next sync.
- File screen: a whole folder can now go up, with no SSH. Use "Upload folder" (a computer with a big screen), or drop a folder on the page or on a folder row. The subfolders stay and are made in the open folder, so a project folder works. Three files go up at a time, through the same upload as one file: large files use chunked sessions up to 20 GB per file, and they go on from the chunks the server has after a dropped connection. One row shows files done, bytes and failures. One failed file does not stop the others, and "Try again" sends the failed files again. When the storage or the server disk has no room, the upload stops with one message, and "Try again" goes on after you free space. A folder of the same name is used as it is, and a file of the same name gets a new name, as for one file. System files such as `.DS_Store` and `Thumbs.db` stay out. In all five languages.
- Skills: a `SKILL.md` whose name is not valid (for example `name: acme-견적`) now gets a clear reason. The warning on the Skills page and on the file screen names the rule: lowercase a to z, 0 to 9 and hyphens, the same as the folder name. Before, the warning said only that the name was not valid. When the AI saves such a file in `skills/`, the confirmation card shows the reason before the save, and the AI gets the reason after a save in `skills/` or in `users/<id>/skills/`, so it can tell you and fix the file.
- Uploads: a "storage full" answer (507) to a large file now ends the upload at once. Before, the browser asked again for about 15 seconds.
- External services: an admin can now ask a member to connect a service as the member's own connection, without seeing the member's key and without signing in as them. Use this for a service that logs every call under the person whose key it is. In Admin › External services › "Requests to members", pick the member and fill in the service as for a team connection: kind, name, address, key or sign-in, the key's header, and usage notes for an API. The member gets an inbox entry and a banner that name the service and the host of its address, and the admin can copy a link to send. The link opens only for that member, signed in, and holds no key. In Settings › External services the member connects it with their own key or signs in, and it becomes their personal connection, made and checked like one they add themselves. Because the admin chooses the address, the connect screen warns, with the host in bold, that the key or sign-in goes to that host, and to go on only if it really is the service's address. The member can also decline. The admin sees whether each request is waiting, connected, declined, withdrawn or expired (after 7 days), and can withdraw a waiting one. The admin never sees the key or the member's connection. Admin › Activity log records requests made, connected, declined and withdrawn. In all five languages. Two additive database migrations (220 and 331); the schema reader level stays 4.
- Background work no longer holds up reading a spreadsheet, a Hangul file or a Word or PowerPoint file. These reads share two office readers with the document text the server remakes in the background (after an update, for files a search left for later, and for search by meaning). Background work could hold both, at its lower priority, so on a busy server a read of a small file could wait about a minute. Now background work takes one reader at a time, the other is left for people, and people go first in the line. Kinds of background work that overlap now run one after the other, so they finish later, also on a quiet server. No root update is needed.
- External services: a large answer that arrives in many small pieces uses much less CPU on the server. With chunked framing the server read the whole answer so far again with every network piece, so the cost grew with the square of the pieces: about 0.5 s of CPU for a 1 MB tool list that came in 1.4 KB pieces, 13 s for the largest list a check can read in its 90 seconds, and 4 s for a 20 MB image. Now it looks only when a piece may have ended a message, and these cost 0.25 s, 0.8 s and 0.25 s. "Check again" still takes as long as the service needs to send its list.

## 0.2.19 — 2026-11-02

[Published release and notes](https://github.com/trina-app/trina-ax/releases/tag/v0.2.19).

**Upgrade note:** take a backup first (Admin > System > Backups > Back up now). No database migrations in this release (the schema reader level stays 4, and 0.2.18 still opens the database). Linux servers need the root update once: mycel-ctl and the update timer's units changed. The old timer installs it at its old time (04:30 plus up to 90 minutes on the server's clock, 13:30–15:00 in Korea on a UTC server) and stops answers still running after 10 minutes; to pick the moment, run `sudo mycel-ctl update` at a quiet time before then. From this release on the timer keeps the team's update window.

- Security, office Mac with this Mac's own Claude login: two ways an AI answer could get an MCP server past the `~/.claude.json` cleanup are closed (both older than this release). A file that starts with a byte-order mark was skipped, though Claude Code reads it, and a very deeply nested file could not be written back, so the planted server stayed and nothing was logged. The server now reads the file as Claude Code does. A file it cannot read or write back is moved whole to `~/TeamAX/config/claude-mcp-backups/moved-…` (only the Mac user can read it), an empty config `{}` takes its place, and Admin › Activity log says so. A `.mcp.json` approval switch set to `1` or `"yes"` instead of `true` is removed too, because Claude Code accepts those, and so is the file's top-level `env` (with a copy, which `teamax claude-mcp restore` lists and puts back): Claude Code copies it into the environment of every command it runs, so a `BASH_ENV` or `ANTHROPIC_BASE_URL` planted there would act outside the sandbox. The engine sandbox no longer lets a turn lock these files (`chflags uchg`, an ACL), and the server unlocks one that was locked before. A cleanup that fails gets its own Activity log entry instead of "removed".
- Office Mac with this Mac's own Claude login (installed without `--claude-token-file`): the server no longer removes MCP settings without a copy or a word. In this mode it empties the MCP settings of the Mac user's `~/.claude.json` (user and project MCP servers, `.mcp.json` approvals, and the copies the Claude CLI keeps of the file) at every start and after every AI answer, so that an MCP server an AI turn might plant there cannot run outside the sandbox. On a Mac someone also used for their own Claude Code this deleted their MCP setups silently (on a test Mac: 2 user servers and the servers of 4 projects), and `--check-only` did not say so. Now everything it removes is first saved to `~/TeamAX/config/claude-mcp-backups/` (only the Mac user can read it, the AI engine cannot; Admin › Activity log names the copy). `office-install.sh` and `--check-only` list what would be removed, by name, and a new install stops until you choose: `--claude-token-file` keeps them (the server never touches `~/.claude.json` in that mode), `--remove-claude-mcp` lets them go, and the installer then saves the copy before the server first starts (it stops if it cannot). `teamax configure --claude-auth local-login` asks the same. `teamax claude-mcp check | backups | restore <copy>` shows them, lists the copies and merges one back without replacing anything, once the server no longer removes them; restore first lists every server in full (command, arguments, env, address) and needs `--yes`, since a copy may hold a server an AI turn planted. Installed offices and automatic updates go on without a question and keep copies from now on.
- Linux servers: the root update (`mycel-update.timer`) now keeps the team's update window. It ran at 04:30 plus up to 90 minutes in the server's own time zone, which is UTC on most Linux servers (13:30–15:00 in Korea), ignored Admin › Team settings › "Automatic update window", and after 10 minutes interrupted the answers still running. The timer now checks every 15 minutes and installs a root release only inside the team's update window in the team's time zone (03:00–05:00 when empty) while no answer is running. It waits for a quiet moment instead of cutting answers off (at most an hour per check, then the next check or the next night); a root release that found no quiet moment for three days is installed in the next window after waiting at most 10 minutes. A check outside the window ends at once, without network. A release that does not start (rolled back) or whose update fails is not downloaded and restarted again at every check: the timer tries it again after 20 hours (the next day's window), then after 44 and 92 hours if it keeps failing, at most once a week; a failure before the root files are in (a download cut short, for example) waits an hour, doubling up to 20 hours. `sudo mycel-ctl status` says until when (Admin › Diagnostics too, from this version on), `sudo mycel-ctl update` tries at once, and a newer release ends the wait. The server's own updater now also leaves a version the server rolled back for 7 days, as documented; it missed the roll-back record before. When the app was rolled back to a version that cannot tell the timer the team's window (0.2.18), the timer reads it with the newer version's own program instead of falling back to 03:00–05:00 on the server's UTC clock. This release changes root files: the old timer installs it, so a server's update to this version still comes at the old time.
- Linux servers: "automatic updates off" and "unsigned versions allowed" no longer stick without anyone seeing them. `sudo mycel-ctl auto-update on|off` and `sudo mycel-ctl allow-unsigned on|off` change them; the units are rendered again each time (and on every root update), so `root/install.json` and the units agree. The installer has `--auto-update` and `--require-signed`, and repair and update keep the update timer as it is now (a plain repair used to turn off a timer that had been turned on by hand). `sudo mycel-ctl status` and Admin › Diagnostics show both, with a warning while automatic updates are off or unsigned versions are accepted, in all five languages; the "needs administrator rights" line no longer says to wait for the timer on a server whose timer is off. A repair of an install that accepts unsigned versions works from the installed copy again when that copy is a signed release.
- Linux servers: a server that skipped a release with root changes now gets them. A release's `needsRoot` compared only with the releases before it, so a server two releases behind could run a new app on old root programs. The feed now names `rootSince`, the oldest release with the same root files; the update timer and the server's own updater compare it with `root/VERSION`. Servers on 0.2.18 or older ignore the field and go by `needsRoot` alone, so `needsRoot` now stays on for every release whose `rootSince` is newer than 0.2.18: such a server never puts a later app-only release on its old root files (after which it refused every release); its update timer installs the root files and the app together. Servers on this version or later still take app-only releases by themselves.
- `sudo mycel-ctl verify-bundle /var/lib/mycel/app/current` checks the version the link points to; it reported every file as missing.
- Office Mac: automatic updates keep the team's update window too. Admin › Team settings › "Automatic update window" did nothing on an office Mac, which updated at 03:00 on the Mac's own clock. The update agent now wakes every 15 minutes and goes on only inside the team's window in the team's time zone (03:00–05:00 when empty), the same setting as a Linux server's; `teamax update time 02:30` (or `02:00-05:00`) now changes that team setting. A time set with `teamax update time` before still counts while the team setting is empty. Admin › System and `teamax update status` show the window with its time zone and the next check in that zone. "Update channel" is gone from Team settings: no server read it (the channel is `teamax update channel` on an office Mac and `server.json` on Linux), and the update window is hidden on a hosted server, which its hosting service updates.
- Office Mac: the nightly update no longer cuts answers off. It waited at most 10 minutes for running answers and then installed, and did not wait at all when the server had not written its answer count lately. Now it waits until the update window closes (at most an hour per run) and leaves the update for the next check; a count the server has not written lately counts as running while the server answers. After three days without a quiet moment it waits at most 10 minutes, as "Update now" does. An empty `update/download/` folder is no longer left behind after an update.
- Grep on very large documents is fast again. To show where each line is ("[p.12]", "[시트 '매출' A12:F12]", "[슬라이드 3]"), the server used to read a matching document's whole text a second time. Now it reads only up to the matching lines, starting from a small index it keeps next to the text of documents of 1 MB or more. A grep over two 50 MB documents took 0.5–0.7 s and about 600 MB of extra server memory; it now takes 35–50 ms and no extra memory, the same as a grep without places (measured on a Mac). Documents whose text was made before this version have no index until they change; they are read in pieces, about 0.1–0.15 s and no extra memory. The labels are the same as before.
- Remaking document text in the background (after an update, for files a search left for later, and for search by meaning) now gives way to people's work. Its converters run at lower CPU and disk priority: on Linux `nice` 10 with the lowest normal disk priority, on a Mac the "utility" level (`nice` has no effect on macOS). A person's grep, uploads and previews go first when the server is busy; an idle server still does the work at full speed. Because a background converter may have to wait, it gets three times as long before it is stopped (its CPU-time limit on Linux is unchanged). No root update is needed.
- A document whose text could not be read in time is no longer left out of grep and search until it changes. When a converter ran out of time or was killed for memory (a busy Mac, where a background converter can wait a long time for the CPU, or a busy server), the server used to keep an empty text for the document. Now it keeps nothing and reads the document again after 2 minutes, then after 8; the last try runs at normal priority with the normal limits. A file that makes its converter crash or use up its CPU time is still kept as "no text" at once. Only after three stopped tries is the document kept as "no text" until it changes, as a file without text always was. Meanwhile grep says how many documents it could not search yet ("search again in a few minutes"), and so does the file screen's content search, in all five languages. A docx or pptx whose headers, comments or notes could not be read in time is read again the same way, instead of being kept with a line saying they were not read.
- External services: "Check again" works for a service whose tool list comes slowly. Higgsfield sends its 1.07 MB list at 17-38 KB/s, so the 30-second limit of a request cut it every time ("The service did not answer within 30 seconds") and the connection kept an older, shorter list (100 of 185 tools). The list is now read for as long as it keeps coming: it fails only when the service sends nothing for 30 seconds, or when the whole list is not in after 90 seconds ("The service did not send its whole tool list within 90 seconds."). Tool calls keep their 30 seconds, and a chat never waits for a check (it uses the saved list).
- External services: a check that fails for now no longer shows a working connection as "Error". When an MCP server with saved tools does not answer in time, cannot be reached for a moment, or answers HTTP 408, 429 or 5xx, the connection is "Connected", keeps its saved tools, and Settings says "Last check failed: … The AI keeps using the tool list from …" (toast: "Could not check the connection."). This also fixes a connection already showing "Error" for such a reason, like a Higgsfield connection the 30 seconds cut. A call that goes through now clears an error a failed check or call left, but never a sign-in that is needed; before, the connection showed "Error" while its tools kept working. In all five languages.
- Chat steps show a short look at a connected service tool's arguments, like Claude Code's tool inputs: "Higgsfield · generate_image (get_cost: true, model: "z_image", prompt: "…")". Flags and numbers come first, so a free price check and the paid run it was for are told apart. Stored keys are hidden. A value whose name says password, token, key, session or cookie (also `pwd`, `jwt`, `apiKey`, `Authorization`, `mfa_code`) shows as "•••", numbers too; counts such as `max_tokens: 4096`, names like `token_type` and plain flags stay readable. A URL's password, an Authorization value, a JWT or a secret query parameter inside any text is hidden too.
- Windows desktop apps on a Linux team server update again. The Windows app updates only from its own team server (`/downloads/latest.yml` and the installer it names), and only an office Mac put those there, so on a Linux server the Windows app never updated. Now a Linux server puts the Windows installer and `latest.yml` of the release it runs into its downloads folder 15 minutes after it starts (an update restarts it) and, while its automatic updates are on, every 6 hours after that. They come from the signed office manifest on the same feed; the signature and both files' size and SHA-256 are checked, a release newer than the server waits until the server has it, one installer is kept (older ones are removed), and nothing is downloaded when the disk would fall under the team folder's write reserve. Windows apps already installed need no reinstall: they find the new version at their next check (every 4 hours) and install it when they quit. Settings › Apps lists the installer too, its hint no longer tells a Linux server's owner to run a Mac command, and Admin › System › Diagnostics has a "Windows app" line that says what the last run did, in all five languages. Now, or on a server without internet: `admin.js desktop-refresh [--from /full/path] [--force]` (docs/INSTALL-LINUX.en.md "Windows app"). No root update is needed.
- A tab that is open while the server updates no longer goes blank. Clicking a page, a side panel or a viewer whose file the update removed now reloads the page once, for the new version, with a spinner meanwhile. It reloads at most once in 5 minutes per tab. It does not reload while something would be lost (a draft, a message that is still being sent or shows "not sent", an answer still streaming, an upload, including one on the file screen, or a recording) or while the server cannot be reached; it waits the same way as the reload after the server reports a new version. A recording counts while it is being transcribed too. The page then shows "This part of the page could not be loaded" with a Reload button, and when a message, an upload or a recording is not finished it says to finish it first, in all five languages. Reloading with that button, or with "Reload" on the new-version notice, puts the text of a message that was not sent back into its chat's input box. The installed web app's service worker keeps one cache per build and deletes the others when a new build starts, so its cache no longer grows by about 15 MB with every release.
- Update cards and the banner (Admin › System, office Mac and server): release notes show their first paragraph, rendered, with "Full release notes" for the rest; before, the whole notes appeared as raw Markdown, several screens long. The office Mac's "Version … is available" banner disappears once the server runs the new version (the page then says "A new version is ready. Reload"), and it follows a changed update time or a pause within 5 minutes, when the tab comes back into view, or at once from the update card. Admin › System › Diagnostics no longer says an office Mac updates by running office-install.sh from a newer zip: it updates itself. In all five languages.
- Windows desktop apps on hosted teams update too. A hosted team server now also puts the Windows installer and `latest.yml` into its downloads folder, 15 minutes after each start (the hosted service's update restarts it), from the signed feed of its own channel and never newer than itself; it does not look again every 6 hours. A server that the channel has passed (a hosted team waiting for its rollout, a self-installed server that has not updated yet) takes its own release's Windows app: from this release on, the feed keeps each release's signed office manifest (`office/<version>/<channel>.json`). For servers on an older release than that, the app follows once they run 0.2.19 or later. Settings › Apps tells the owner of a hosted team that the app appears by itself and that Admin › System › Diagnostics ("Windows app") says why when it does not; on a hosted team that line names no server command, in all five languages.

## 0.2.18 — 2026-11-01

[Published release and notes](https://github.com/trina-app/trina-ax/releases/tag/v0.2.18).

**Upgrade note:** two small database migrations (329 and 330, additions only: 329 adds a column to `chat_seen_urls`, 330 two columns and a trigger to `integrations`; the previous version still opens the database; the schema reader level stays 4).
