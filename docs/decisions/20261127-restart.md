# Owners and admins restart the AI or the app from Admin; a watchdog restarts a hung server

- Date: 2026-11-27
- Status: accepted
- Supersedes: none
- Branch: feat/restart-app, feat/restart-root (the owner: plan, independent review, build)

- **Ask:** when answers hang or the app is stuck, the team needed SSH (`systemctl restart`) or the hosting operator.
  Give owners and admins a restart in the app, and restart a server that stops answering by itself.
- **Rule, the button:** Admin › System › Health has one row "다시 시작…". The dialog asks what (AI only, or the whole
  app) and when; then the password or Google check (`admin-reauth`).
  - "AI only" restarts the engine launcher (`{"op":"restart"}`: new turns wait, running answers end with the restart
    message and Try again, the launcher exits and its supervisor starts it again). Shown only when the server talks
    to an installed launcher whose status lists `restart` in `ops` (Linux, Docker, hosted, Mac installs). On an
    office Mac and a dev server the launcher is the server's child: "the whole app" covers it.
  - "The whole app" stops the server (`SIGTERM`); its supervisor starts it again. Offered only when one exists:
    `MYCEL_SUPERVISOR_PID` set (the bootstrap) or office mode (`office.js run`). A plain `bun run dev` has none.
  - "When answers finish" waits at most 10 minutes (the hosted reboot's wait), showing only how many answers run,
    never whose. While it waits the dialog's row offers "Restart now" (owners, with the password again, as for "Update now anyway") and "Don't restart" (the
    owner, or the admin who asked for it: an admin cannot call off someone else's restart), scheduled
    runs do not start (the update-wait marker, with its own `kind: "restart"` and its own words), and other
    maintenance (backup, update, restore) says a restart is waiting. It waits for answers only: team-file jobs and
    video renders that run then are marked failed at the next start, as after an update, and the dialog does not
    promise otherwise.
  - Owners may also choose "Restart now" (running answers end with Try again). Admins only get "when answers finish":
    update, restore and diagnostics stay the owner's, and an admin must not cut the owner's answers.
  - Office mode's watchdog never acts while the office update agent runs (it stops and starts the server itself), as
    the bootstrap's never acts on a pending or forwarded version.
  - Refused: another maintenance task runs (the ops lock), an update waits or runs (this server's, root's, office's),
    a restore is prepared, `app/state.json` `pending` or `forward` is the running version (the update is still being
    checked: an exit then counts towards a roll-back), `app/current` is another version, the option is not offered.
  - Limit: 5 accepted requests an hour for the team, at least 2 minutes apart, every kind together, counted from
    the audit log (`system.restart_requested`) so a restart does not reset it. Refused requests and watchdog
    restarts do not count. Audit: `system.restart_requested {what, when}`, `system.restart_cancelled`,
    `system.restarted {what}` (the app's after its next start).
- **Rule, the watchdog:** the bootstrap (Linux, Docker, hosted, Mac installs) and the office supervisor watch a
  server that runs normally. After a start answered `/api/health` ok once, every 30 s the same health check the
  update watch uses (3 s timeout); 10 failures in a row (about 5 minutes) is a hang.
  - Kill switch `server.json` `watchdog: {kill: true}` (office Mac: `TEAMAX_WATCHDOG_KILL` in `config/office.env`,
    because office rewrites server.json at every start), read at every hang. Off by default at first: the hang is
    logged only, so QA and potenlab could watch the log first.
  - Since 2026-11-27 the office Mac kills by default (`TEAMAX_WATCHDOG_KILL=0` turns it off). QA on qa.trina.app
    passed (a hang found after about 5 minutes, SIGTERM then SIGKILL, restart, the 3-an-hour cap, the give-up), and a
    check of the code found nothing that holds the event loop for minutes once the server answered: backups,
    conversions, updates, migrations, uploads and zips, search and the file list run in child processes or in async
    chunks. The check moved three long pieces off the loop: the restore's integrity check of the staged copy (now in
    a child process), the file list's pass after a rule change (a pause every 100 files, no sync per commit) and its
    follow-up of a moved folder (one commit).
  - Linux, Docker and Mac installs stay log-only by default for now: a big file is copied in one synchronous step
    (`copyFileSync`: the version kept when a file is replaced, a file copy, a version restore, an upload across
    volumes). APFS clones it at once (the office Mac), but ext4 copies every byte, and a 10–20 GB file on a slow
    cloud disk holds the server for over 5 minutes. Those copies move off the event loop first; then the default
    flips there too.
  - Never counted: a start that has not answered yet (a restore at start, migrations before listening), a 503
    `migrating` answer, a pending or forwarded version (they keep their own watch). Exit 75 and the stop when no
    version can run are unchanged.
  - At most 3 kills an hour, counted in the supervisor's memory only: a restart of the bootstrap or of `office.js run`
    (the service, the computer) starts the count again. Then it gives up: `state.json` `liveness {gaveUp, since, detail}` until the next healthy
    answer, not until the hour passes (a server with a broken database would be cut every hour); the give-up is on disk,
    so it holds across a restart of the supervisor. `mycel-ctl status`
    and Admin › System › Health show it (office Mac: `data/liveness.json`, shown in Health). The control plane's TenantStatus does not carry it in v1.
- **Why:** a restart reuses what exists (the planned restart of an update, the launcher's orderly stop of 11-17), so
  there is no new path to root: the app never asks root for anything. Kill-off by default because nobody has measured
  how long the event loop of a big team stalls.
- **Left out of v1 (review):** a team-side "restart the computer" request to the control plane (a hung server cannot
  send it; one that can is fixed by restarting the app; the operator's reboot button covers the rest), `WatchdogSec`
  on the launcher unit (nothing in `native/` speaks sd_notify; "AI only" covers it), an AI tool `restart_trina`
  (Claude Code has none), the give-up in the CP status report, scheduled restarts, a restart for members.
- **Version impact:** minor (0.21.0), a new feature. Root release: the bootstrap and the launcher change. The app
  part works without the root part ("AI only" is hidden until the launcher advertises it).
