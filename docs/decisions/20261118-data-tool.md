# The AI calculates over data files on every install: query_data

- Date: 2026-11-18
- Status: accepted
- Supersedes: none (narrows what the dev environment is for: "Dev environment on srt, behind a flag", 2026-11-04)
- Branch: feat/data-tool (QA TC-4913; second limits audit, finding N1)

Plan: docs/AGENTS/plan/20261118-1150-query-data.md.

- **Ask:** without the dev environment (an office Mac, teams from before 2026-11-06, Ubuntu / Debian 12 servers) the AI
  refused everyday data work on a 50,000-row CSV or xlsx: a pivot, totals, a top 5, splitting a CSV by region, a
  monthly chart ("the heavier data-processing option isn't available"). 7 of 42 audit tasks. Claude Code does each with
  one `python` or `awk` call. The app map also told the AI that the dev environment is where "the AI does heavier work
  itself, e.g. big data files".
- **Shape:** one built-in tool, `query_data { paths, sql?, sheet?, header_row?, show_rows?, save_as?, split_by? }`.
  Without `sql` it shows the tables, column names and types and the first rows; with `sql` it runs one SQLite query
  over them. Small results come back inline (50 rows by default, at most 500, the table cut to about 30,000 characters
  so the engine never cuts it silently); `save_as` saves the whole result as .csv (UTF-8 with a BOM, so Excel shows
  Korean), .tsv or .xlsx; `split_by` makes one file per value of a result column ("<name> - <value>.csv", or
  `{value}` placed in the name), at most 100 files.
- **Formats:** CSV and TSV (UTF-8, UTF-16 by its BOM, else CP949; the delimiter of , tab ; | that the first line has
  most of), xlsx / xls / ods (every sheet a table: data, data_2, ...; `sheet` loads one), JSON (an array of records, or
  an object holding one; nested values as JSON text) and JSONL. One file is the table `data`; several are t1, t2, ...
- **Types:** a column whose every value is a number is INTEGER or REAL ("1,234" counts; a leading zero like "007" or
  more than 15 digits stays text, so codes and card numbers keep their form); everything else TEXT; empty cells NULL.
  Dates stay as written; a sheet's dates become "YYYY-MM-DD" (the worker runs in UTC so the day is the one shown).
- **Engine: bun:sqlite**, already in the stack, inside the office worker (the bun child that reads spreadsheets). No
  new binary, package, licence or bundle step. DuckDB (MIT, so licence-compatible) was the other option: a 30-60 MB
  native library for each of Mac arm64/x64, Linux x64/arm64 and Windows, listed with sha256s in
  scripts/system/packages.json and shipped as a root update, loaded as a native module in the worker. For office data
  SQLite on disk is fast enough: 4,000,000 rows (217 MB) loaded and grouped in 26 s at 770 MB of memory, 50,000 rows
  with a three-way split in under a second (M-series Mac).
- **Isolation and limits:** the inputs the person may read are copied into an empty work folder; the worker runs there
  through tools/isolate.ts (macOS sandbox-exec, Linux bwrap and the converter cgroup): no network, only the work folder
  and its own script readable. Limits sized for a 200 MB file: 180 s, 2 GB of memory (the office worker's), the work
  folder at most 4 times the inputs plus 512 MB, 16 MB of answer; two queries at a time on the server, another waits
  up to 60 s and then hears "try again in a moment". Per file the read limit (200 MB without a plan), a spreadsheet also
  the in-process parse limit (32 MB where limits apply), 400 MB per call in all.
- **SQL:** one statement (a ";" outside quotes and comments may only end it), it must start with SELECT, WITH or
  VALUES, and runs with `PRAGMA query_only` as a subquery (repeated result names stay apart: "x", "x:1"). SQLite's
  extension loading is not there. The database holds only the copies, so a query cannot reach any other file.
- **Who sees what:** each input is opened with the person's read access (a file they cannot open answers like a
  missing one) and joins the turn's read scope, read hashes and the answer's sources like a read; a shared chat's read
  card sees `paths` (PATH_ARGS) and counts `save_as` as where it writes (WRITE_TARGET_ARGS). Saving goes through
  make_file's save path (placeProduced: write access checked again per file, conflict copies, versions, file events),
  after the wider-audience check for the inputs at the result's folder, asked before the query runs so a "no" costs
  nothing. Never into a skills folder. Allowed in shared chats, rooms, guests (in their folders) and confidential chats:
  it only reads team files and writes like make_file.
- **Budget:** what one answer saves through query_data has its own cap (500 MB, 200 files), not the turn's write
  limits for text the AI typed (50 MB, 200 files), as unzip_file: the content is the person's own data, and a split of
  a 150 MB export is normal. A guest keeps the turn's normal limits.
- **Prompt:** a rule (QUERY_DATA_RULE) and the tool's description tell the AI to use it for any calculation over a data
  file instead of refusing, estimating, counting with grep or retyping rows; a chart = the figures saved as .csv, then
  make_file's Excel chart. The app map's dev-environment words no longer name big data files.
- **Out:** chart pictures (audit N4), styling or formulas in the saved .xlsx (make_file does that from a saved .csv),
  Google Sheets and files shared by link (/f/...).
