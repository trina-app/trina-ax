# Long JSON reads stay fast; UTF-16 text reads and greps

- Date (UTC): 2026-11-18 15:00
- Branch: `fix/json-tidy-utf16` (from the head of `fix/read-long-lines`, 440c4c8de, PR #1282)
- Status: in progress
- Where: Team AX core, `server/src/files/`. Why: the AI's read and grep live there (see docs/REPOSITORY-RULES.md)
- Version impact: patch

## Goal

QA TC-4950 (found in the review of #1282): (1) the pretty-printed view of a one-line JSON file is worked out again for
every piece the AI reads, about 0.5 s per call on 18 MB, so reading it through stalls the server for minutes. (2) grep
finds text in a UTF-16 file (ripgrep reads it through its byte-order mark) and tells the AI to read it with
offset/char_offset, but read refuses the file as binary; a UTF-16 file without a byte-order mark is skipped by grep
with no word at all.

## Scope

In:
- read: the text of a file and its views (lines, pretty JSON) are kept by the file's content hash for the next reads,
  in a bounded cache; the first view itself is cheaper (no extra copies of the text).
- read: UTF-16 text (with a byte-order mark, or plainly UTF-16 without one) is shown as text, with the same lines and
  character positions grep reports. edit says the file is UTF-16 instead of "binary".
- grep on one file that finds nothing: when the file is UTF-16 without a byte-order mark, the result says so and to
  read it.

Out: a folder-wide grep does not open every file to look for UTF-16 without a byte-order mark (cost).

## Steps

1. read-lines.ts: lines split once, exact-JSON check without a copy, a `ReadViews` cache; service.ts uses it.
2. extract.ts: UTF-16 decode; service.ts: edit's message, grep's note.
3. Unit tests and a benchmark test (per-piece time on an 18 MB one-line JSON).
