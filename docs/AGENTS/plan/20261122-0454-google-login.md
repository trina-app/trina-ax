# People can sign in to the team with their Google account

- Date (UTC): 2026-11-22 04:54
- Branch: `feat/google-login` (part A1; A2, B, C and D get their own branches and link this plan)
- Status: built, not merged yet (A1, A2, B, C and D, then sign-up with Google on top: `feat/google-signup`)
- Where: trina-ax (`server/src/auth/`, the Google callback route in `server/src/routes/drive.ts`, `web/src/pages/Auth.tsx`
  and Settings › Security, Admin › Members, `desktop/`, `mobile/`, `shared/src/api/auth.ts`, a new
  `shared/src/cloud-protocol/google-signin.ts`) and trina-cloud (a sign-in broker beside `src/drive-broker/`). Why:
  signing in works the same on every install; the hosting service only lends a Google client to hosted teams that have
  none, as it already does for Google Drive.
- Version impact: minor. New endpoints, one add-only migration and a new optional way to sign in; password sign-in does
  not change.

## Goal

Today people sign in with a username and a password only (`POST /api/auth/login`, `server/src/auth/accounts.ts:208`).
Companies on Google Workspace want their staff to press **Sign in with Google** every day instead of typing a password.

The hard part is the address. Google accepts only exact return addresses (no `*.trina.app`), and every team has its own
address. The Google connectors already solve this in two ways, and sign-in uses the same two:

- A server with its **own Google client** uses it directly, with the return address it already registered.
- A **hosted team without one** borrows the hosting service's client through account.trina.app, which has one fixed
  return address.

## Scope

In:
- **Connect**: a signed-in person connects their Google account in Settings › Security. It asks for their current
  password first, and is refused in a temporary-password session, during a forced password change, and for guests.
  The person gets an Inbox notice when a Google account is connected.
- **Sign in**: on the login page, **Sign in with Google** signs in the person whose account that Google account is
  connected to.
- **See and remove**: Settings › Security lists the connected Google account (address, when connected, last used) with
  **Disconnect**. Admin › Members shows "Google" beside a person and lets an admin remove it (the usual rules: nobody
  acts on the owner, only the owner acts on admins).
- **Admin resets disconnect Google**: an admin's temporary password and a completed reset link remove the person's
  Google connection, so a reset after a suspected break-in really locks the old ways out.
- Admin › Team settings: one row **Sign in with Google**, on or off (on by default when a Google client is available).
- Self-installed servers: works when the server has its own Google client.
- One docs site page, one `changes/google-login.md` note per PR.

Out (later, each with its own plan):
- **Joining with Google and accounts without a password.** Everyone keeps a password in this version, so the owner
  handover rule ("There is no sign-in without a password to bypass it", `docs/DECISIONS.md` "W6 — Onboarding v6: easy
  owner handover") and every password re-check stay as they are. See Open questions.
- Joining without an invite because the Google account ends in `@company.com`.
- "Google only" (passwords off), SCIM, or ending Trina sessions when Google Workspace suspends someone.
- Self-installed servers signing in through the hosting service (B is for hosted teams only).
- Guests. Microsoft and other providers (the table takes a `provider`, so they can come later).
- Matching an account by its e-mail. Never (see Decisions).

## How it works

### Identity

- New table `login_identities` (migration `131_a_login_identities.sql`): `user_id`, `provider` (`'google'`), `subject`
  (Google's `sub`), `email` and `hd` as of the last sign-in (shown, never used to match), `linked_at`,
  `last_used_at`. `UNIQUE(provider, subject)`, `UNIQUE(user_id, provider)`.
- It is a sign-in credential like `users.password_hash`: INSERT and DELETE triggers advance `safe_ops_policy`'s
  generation (as `server/migrations/319_c_policy_epoch.sql` does for password changes), and account removal deletes the
  rows (`registerAccountCleanup`, `server/src/auth/account-removal.ts:30`; users are tombstones, so no cascade runs).
- An account is found only by `(provider, subject)`. Never by e-mail: e-mails here are free text, not unique, and the
  person can edit their own (`server/migrations/001_init.sql:7`, `server/src/routes/auth.ts:101-109`).
- Google must answer `email_verified: true`.

### Endpoints

- `POST /api/me/google/connect` (`auth: 'user'`, not in `GUEST_ENDPOINTS`, no `allowWhilePasswordChange`;
  body `{ password }`) → `{ url }`. The password is checked like the current password in `changePassword`
  (`accounts.ts:277-287`) and failures count like a re-check (`service.ts:154-169`).
- `DELETE /api/me/google` (`auth: 'user'`) and `DELETE /api/admin/users/:id/google` (the `guard` rules,
  `server/src/admin/users.ts:63-70`).
- `POST /api/auth/google/start` (public, body `{ next? }`) → `{ url }`. Sign-in only. Limited per IP, with a cap on open
  flows, because nobody is known yet (Drive's limit is per person, `server/src/integrations/google-drive/oauth.ts:214`).

### Flow

- New table `google_signin_flows` (same migration): `state_hash`, sealed nonce and PKCE verifier, `intent`
  (`signin` | `connect`), `client`, `binding_hash`, `user_id` and `session_id` (connect only), `config_key`, `mode`
  (direct | broker), `next` (a checked relative path, so `?next=` survives as in `web/src/App.tsx:350`), `status`,
  `expires_at` (10 minutes). Drive's flow tables cannot be reused: they require a user and a session
  (`server/migrations/312_c_google_drive.sql:17-30`).
- **Binding** (nobody can finish a flow someone else started): the start sets a short cookie named by the `cookieFor`
  rule (`__Host-gsi` on https, a dev name on plain http; `server/src/auth/service.ts:100-103`), HttpOnly, SameSite=Lax,
  10 minutes, cleared on return. The flow keeps its hash. A second tab replaces the first tab's flow.
- **Google request**: scopes `openid email profile`, `prompt=select_account`, nonce, PKCE, no offline access, no refresh
  token kept. The id_token is checked for `iss`, `aud`, `azp`, `exp`, `nonce` and `email_verified`. Nothing from Google
  is stored except the identity row.
- **Return**
  - Direct mode: Google returns to the address the server already registered, `/api/integrations/google-drive/callback`
    (required by `server/src/integrations/google-drive/config.ts:13-16`). That route looks the state up in
    `google_signin_flows` first, then in the Drive flows as today. A company that set up its Google client registers
    nothing new.
  - Broker mode: account.trina.app sends the browser to `/api/auth/google/return?state=…&handoff=…` (Google never sees
    this address).
- **Results**
  - signin: connected, active and not under a forced password change → `AuthService.signIn` (`service.ts:242`), then
    `next` or `/`. Not connected → a page saying this Google account is not connected to this team: sign in with your
    password and connect it in Settings › Security. Turned off → the same `account_off` answer as a password sign-in.
    Temporary password or forced change → "Sign in with your password first".
  - connect: the same session as the start, the person is still active and not a guest, and the Google account is not
    connected to anyone else in the team → connect, Inbox notice, audit.
- Bad states count per IP through `tokenGuard` (`accounts.ts:91`). Audit: `auth.login` with `method: 'google'`,
  `auth.identity.link`, `auth.identity.unlink`. No code, token, id_token, nonce or handoff in logs or audit.
- Demo mode: the new endpoints go in `FREE_ROAM_FENCE` as `'account'` (`server/src/demo/guard.ts:114`), and the button
  is hidden.

### Where the Google client comes from, and when the button shows

- The server's own client is `googleDriveOf(ctx).config`: a company's own Google app (`own-app.ts`, on hosted or
  broker-served servers), the in-app setup (`admin-setup.ts`) or `MYCEL_GOOGLE_DRIVE_CLIENT_FILE`. With one → direct.
- Else, on a hosted team, the hosting service when it answers that it serves this team → broker (part B).
- The button shows only when there is a client, the team row is on, the page is a plain browser (`clientKind()` is
  `web`; the apps come in C and D), the page's origin is the client's return origin and the client is not stale
  (`own-app.ts:110-112`), and not in demo mode. People who reach the server by an office, Tailscale or LAN address
  sign in with the password there.

## Steps (each its own PR into `dev`)

1. **A1. Identity, connect, sign in** (this branch, built): migration 131 (`login_identities`, `google_signin_flows`,
   the policy triggers), `server/src/auth/google-login.ts` (start, connect with the password, the return through the
   Drive callback, the binding cookie, the id_token checks), `GET /api/setup` `googleSignIn`, `GET`/`DELETE
   /api/me/google`, admin resets and account removal dropping the rows, the demo fence, the sign-in page's button and
   `?google=` line, Settings › Security & devices › Google account, six languages, unit and web e2e tests, the two
   decision files and `changes/google-login.md`. Audit names are `auth.google_connected` and
   `auth.google_disconnected`. `google_signin_flows` has no `client` or `mode` column yet: B and C add what they need.
2. **A2. Admin and docs**: the Admin › Team settings row (on or off), `DELETE /api/admin/users/:id/google` and the
   "Google" label with Remove in Admin › Members (the `guard` rules), the Inbox notice when a Google account is
   connected, the docs site page.
   After A: hosted teams with their own Google app and self-installed servers with a Google client, in a browser.
3. **B. Hosting service sign-in, hosted teams only.**
   - Google: a client in an identity-only Google project (no sensitive or restricted scopes), not trina-ax-513907.
   - trina-ax: `shared/src/cloud-protocol/google-signin.ts`, self-contained (no imports) with its own signing string
     `trina-google-signin-v1`, so a Drive signature never counts here. The team server sets the nonce. The control
     plane hands back Google's **raw id_token**, and the team server checks its signature against Google's keys plus
     `iss`, `aud` (the broker's client id), `azp`, `exp` and `nonce`. The control plane can relay a sign-in, not make one
     up.
   - trina-cloud: `src/google-signin/` beside `src/drive-broker/`, modeled on the Slack broker's sign-in, which exists
     only on `origin/dev` (= `deploy/live-dev-slack-http`), not on `deploy/live-plus-dev`. A new flag in
     `scripts/sync-protocol.ts` for the new contract file, a migration for its flow table, then deploy.
   - After B: every hosted team, in a browser.
4. **C. Desktop app.** The login page in the app makes a random secret and sends only its hash at the start; the return
   page opens `trina-ax://open?url=<team>/login/google#code=…`, and only that secret redeems the code (the RFC 8252 /
   PKCE shape), so the system browser is never signed in. A redeem into an app signed in as someone else is refused
   (the 409 rule, `server/src/auth/app-signin.ts:86-94`); on a LAN address the cookie is mirrored
   (`desktop/src/main/direct.ts:172`). Connecting from the app reuses the held-then-claim pattern of the connectors
   (`oauth.ts:329`, `:379`). Skipping the "Connect to {host}?" screen for this link changes
   `docs/decisions/20261116-desktop-first-onboarding.md`.
5. **D. Phone app** (store release). A new bridge capability `google-signin-v1`: open the Google step with
   `openAuthSessionAsync` (ASWebAuthenticationSession / Custom Tabs), take the code from the result address and redeem
   inside the WebView, so the cookie lands in the app. Builds without the capability show no button.

## Risks

- **Google's free sign-in.** Google's help ("Manage App Audience") says requests for only `openid`, `email` and
  `profile` show no "unverified app" screen and are not in the 100-user cap. A project that also asks restricted
  scopes is not clearly covered, hence the identity-only project for B. A company's own app (A) is the company's
  choice; an Internal app has no review and no cap.
- **Control plane branch.** `~/.claude/team-ax-family-rule.md` names `deploy/live-plus-dev` (Slack:
  `deploy/live-dev-slack`) as the console's production source, while the code B copies is on `origin/dev`. Confirm what
  production runs before B.
- **Offboarding.** Someone suspended in Google Workspace keeps their Trina session (up to 30 days) and their password
  until an admin turns them off in Trina. Say so in the docs.
- **Wording.** "Google sign-in" already names the connectors' Google app (`gsign.*`,
  `web/src/components/integrations/GoogleSignInRow.tsx`). Login text says "Sign in with Google" and "Connect Google
  account", never "Google sign-in".
- **App Store guideline 4.8** (another sign-in option, such as Sign in with Apple, when an app offers a third-party
  one). Check the exemption for business apps that sign in to an existing company account before D.
- **Migration 131.** Check `server/migrations/` on `dev` right before the merge.
- **Relay.** Start and return go through the relay like Drive's. The binding cookie has no Domain, so it stays on
  `<team>.trina.app`.
