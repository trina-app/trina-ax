## Goal

QA case: in a chat shared with qa-member, the asker says "내 폴더의 제안서 HTML(이미지 폴더 포함)로 PPT 만들어 줘".
Today the AI cannot bring the asker's HTML and its images folder into the chat's work folder, so box_shell cannot
build the deck from it. After P2 the one way in is `copy_files` to `chat:work/`, and the one way out is `copy_files`
to `chat:files/` (attached to the answer) or to a team folder.

## What copy_files does with a chat place (one code path: `server/src/chat/places-copy.ts`)

A call whose `paths` or `to_folder` names a chat place (`chat:files/…`, `chat:work/…`) goes to the places copy; any
other call stays the team copy of `tools/file-moves.ts` unchanged. Mixed sources into a team folder: the team ones
through the team copy, the chat ones through the places copy, one result.

| from \ to | team folder | `chat:work/<dir>/` | `chat:files/` |
|---|---|---|---|
| team file | (team copy) | `writeIntoWork` file; shared chat: the shared read card first (call() → confirmSharedRead), its yes a `y` group; the sources recorded under the workspace key | attach (createFromAi + attachToAnswer); shared read card first; 1 GB cap and the turn's limits |
| team folder | (team copy: refused, files only) | `writeIntoWork` folder: every entry the asker may read; links, pipes, hard links skipped; each `boundaryFolders()` folder under it the asker may read is a source (as `make_zip`: sharedSources) | refused: chat files have no folders |
| chat file | the asker's write rights, the wider-audience card with the chat as source (save_chat_file's code) | `writeIntoWork` file from the checked chat file; refused when it is carried only by a hidden (k) answer | refused: it is in this chat already |
| work file | the asker's write rights, the wider-audience card with the work folder's sources (personal: the person; shared: the chat and its copied-in groups); save_work_file's code | refused: use box_shell `cp` | attach (save_work_file's chat mode) |
| work folder | refused (zip it in box_shell first) | refused | refused |

Rules over the table:
- **Where each place is writable** is the resolver's (files/places.ts). It gains `use: 'write'` for `chat:work/`:
  writable where box_shell's commands run in a work folder for this person (personal or people-shared chat), even when
  the folder is not made yet (writeIntoWork makes it: the one place that may create). Project chats: `chat:files/` is
  read-only (the project folder is the only save place, owner decision 2026-11-21) and there is no work folder.
  Personal chats: `chat:files/` is not a save place (review fix 1). A turn with a k group attaches nothing.
- **The k refusal:** a chat file carried only by hidden answers is never copied anywhere (P1 refuses its read; the
  copy uses the same check), and in a k turn nothing is attached.
- **viaLink:** when `writeIntoWork` says the copy went through a link a command made, the result tells the AI that the
  file is not in the work folder itself.
- **Limits:** writeIntoWork's 1 GB / 2,000 files per call and each file at most the read limit, plus what the turn may
  still write (turnWriteLimits): the copy counts against it. Attach: 1 GB (`CHAT_FILE_AI_MAX`) and the turn's limit.
- **Cards:** no new card. Into `chat:work/` and `chat:files/` of a shared chat: the existing shared read card. Out to a
  team folder: the existing wider-audience card (confirmWidening). After a room read in a personal chat: copy_files'
  own copy card (as the team copy asks then) before anything is written to a team folder.

## The old tools become aliases

`save_chat_file {file, save_as}` and `save_work_file {path, save_as}` keep their schemas, their refusals before the
card, their cards and their result texts (the golden tests of #198/#200 run unchanged). Their call bodies are the
places copy's two routes (`chatFileToTeam`, `workToTeam`, `workToChat`), the very code copy_files runs, so a card, a
step line and an audit row look the same for both. They leave the tool list in P5.

## chat:work/ gets list, glob and grep (moved here from P1)

FileService.callPlace: `list chat:work/<dir>` (names, sizes, folders marked; nothing opened), `glob` (a walk of at most
5,000 entries), `grep` (text files at most 4 MB each, opened with the work folder's checked open: O_NOFOLLOW, one link,
the kernel path inside the folder). A link is shown as a link and never followed. Every read, list, glob and grep of
`chat:work/` in a shared chat goes through `exec.workRead` → `noteSharedReads(space)`, which re-records the copied-in
groups (runner noteCopiedIn) before anything is given; it now matches list, glob and grep too.

## query_data takes chat places

QA found the AI trying `query_data` on a chat file and being refused. `query_data`'s `paths` may name `chat:files/…`
and `chat:work/…`: each such input is copied (the chat file through ChatFiles.open, the work file through
copyWorkFile) into the call's own work folder before anything else, and then calculated over like a team file. Its
source is the chat (or the person, for a personal chat's work folder); it never enters the answer's team file list.

## Texts

copy_files' description and schema say the three places and that folders copy into `chat:work/`. box_shell's two
descriptions and the prompt's work-folder rule say: bring files in with `copy_files` to `chat:work/`; hand a finished
file over with `copy_files` to `chat:files/` (shared chat) or a team folder. placeRefusal for move/rename of a chat
place suggests copy_files.

## Risks

- A folder copy out of `chat:work/` is refused for now (only files): a zip made in box_shell is the way.
- The work folder's listing reads names by path: a folder swapped for a link between the check and the readdir could
  show the names of the link's target (names only; every open is the checked one). Each folder's real path is
  checked before and after its readdir.
