## Goal

The owner's ask (2026-11-23): "Each room gets its own email address, so order notices, inquiries and other emails
forwarded there show up in the room as cards. Set up a filter once in Gmail or Outlook, and those emails arrive
automatically for the whole team to read and reply to in the room. Every room has its own address, and if it ever
leaks you can replace it with a new one in a click."

For: teams that get order notices, customer inquiries, supplier mail and alerts in one person's inbox today. After
this, one person sets a mail filter once, and the whole room sees each mail as a card, talks about it in its thread and
asks the AI about it.

## 1. Address format

**Recommendation: `<token>@in.<domain>`** (hosted: `in.trina.app`). The same as the room apps plan.

- Token: 26 characters from `a-z2-7` (base32, lowercase), 130 random bits. Mail addresses are case-insensitive in
  practice, so lowercase only. Example shape: `k7q2m9x4p8w3t6v5n1c4hj2abd@in.trina.app`.
- The token is also the inbox key: the mailbox keeps `sha256(token)` → (team id, app id) and nothing else about the room.
- The room name is not in the address: an address that leaks tells nothing about the team or the room.
- The address is shown again to the people who manage the app (vault-sealed, rekeyed), as the apps' address.

Not chosen:

| option | why not |
|---|---|
| `<token>@<team>.trina.app` | Each team label needs its own MX and mail routing setup; Cloudflare Email Routing works per configured domain or subdomain, not by wildcard (verify in the spike). It also shows the team name. |
| `<team>.<token>@in.trina.app` | Shows the team name; a rename changes every address. |
| A readable prefix (`orders.<token>@…`) | Nice, but the prefix is free text people may fill with private words. Owner question 6. |
| A custom domain per team (`orders@acme.com`) | The team's own MX and DNS; support load. Later, if asked. |

**Self-hosted and office teams.** A server without a public domain cannot take mail: receiving SMTP needs a public IP,
port 25 and an MX record. So **every** server gets mail the same way, by pulling from the mailbox. This works behind
NAT and for office-only servers, but needs a registration with the hosting service (the relay team key):

- Hosted teams: on, automatic.
- Self-installed servers that joined with a claim code (the relay add-on): on, the same as hosted.
- A server with its own public host and no registration, or an office-only server that never registered: the Email
  kind shows "Email needs this server to be connected to the Trina service." with the role-based screen the apps have
  for "No public address". **(changed)** The apps plan said "a server with its own public address keeps direct
  delivery". For mail there is no direct delivery: the server cannot be an MX.
- An operator who runs their own relay and edition (another `<domain>`) runs their own Worker and mailbox from the same
  source, or leaves the kind off.

## 2. Inbound mail path

**Recommendation: Cloudflare Email Routing → Email Worker → mailbox queue → team server pulls.**

```
sender ─SMTP─▶ MX in.<domain> (Cloudflare Email Routing)
                 └▶ Email Worker: size check, token lookup, parse, seal
                       └▶ mailbox queue (one per team, sealed items, ≤ 24 h)
team server ◀── signed long poll (≤ 25 s) ── pulls, opens, acks ──▶ item deleted at once
                 └▶ rooms/apps: card or thread reply in the room
```

**Why pull, not a push through the relay to `/in/`:** once the Worker accepts a mail (SMTP 250), the sender's server
stops retrying, so Trina must keep the mail until the team has it. A sleeping trial team, a team server that restarts
and an office-only server all need a queue. Pull with a queue covers every case with one path; a push needs the queue
anyway for the failures.

### DNS on `in.<domain>`

- `MX in` → Cloudflare Email Routing (the three records Cloudflare gives). The apex MX stays as it is.
- `TXT in` SPF: `v=spf1 -all`. Nothing sends mail from `in.<domain>`.
- `TXT _dmarc.in` : `v=DMARC1; p=reject`. Nobody can send mail that claims to be from `@in.<domain>`.
- No DKIM key: the domain never sends.

### The Email Worker (stateless, in memory only)

1. `message.rawSize` > 25 MiB (v1) → `setReject("552 5.3.4 Message too big")`.
2. Local part must match the token shape, else `550 5.1.1`. `sha256(token)` lookup in the mailbox index; unknown,
   rotated or removed → `550 5.1.1 No such address`. The same answer for every refusal.
3. Limits (per token and per team, below) → over them: `451 4.7.1 Try again later` (the sender retries).
4. Parse the MIME (a maintained parser, e.g. `postal-mime`): headers we keep, `text/plain` and `text/html` parts,
   the attachment list. v1 drops attachment bytes here.
5. Build a JSON item ≤ 1 MiB (the text parts are cut to fit, with a "cut" flag), seal it to the team's mailbox public
   key, put it in the team's queue.
6. The queue is full (over 2,000 items or 50 MB) → `452 4.2.2 Mailbox full` (the sender retries).

The spike checks what Cloudflare does when the Worker throws (temporary or permanent failure) and makes every error
path a clear temporary failure.

### The mailbox (hosting service)

As in the apps plan: the team server makes an X25519 key pair, keeps the private key in the credentials vault, and
registers the public key with a call signed by the relay team key. Items are sealed with
`X25519-HKDF-SHA256-A256GCM`, with the inbox id, the item id and the receive time in the associated data. Pull: signed
long poll ≤ 25 s, explicit acks, an acked item is deleted at once. At least once: the server dedupes by item id for 24
hours, and by `Message-ID` per app for 7 days.

**New here (the gap the apps plan left):** the token index.

- `PUT inbox/addresses/<sha256(token)>` (create), `DELETE …` (remove): signed by the team key. The cloud never sees a
  token in clear, only its hash; the Worker hashes the local part to look it up.
- Rotation: the team server removes the old hash first, then adds the new one, and shows the new address only when both
  calls answer OK. If the mailbox cannot be reached, "Get a new address" fails with "Try again in a minute." The old
  address is refused from the moment of the delete.
- Items already in the queue under the old address are still delivered (they came before the change).

**Sleeping teams (F2).** An item for a sleeping team makes the mailbox ask the control plane to wake it (the same wake
call as the relay's, its own key). The mail waits in the queue; the card comes when the server is up. Paid teams do
not sleep.

**Where it runs:** a Worker with one Durable Object per team as the queue (SQLite storage), on the hosting service's
Cloudflare account. The Worker and the mailbox source are in core under `mailbox/` (MIT, like `relay/`), so an operator
of another edition can run their own; the deployment and keys are in the hosting service's repo.

### Alternatives considered

| option | pro | con |
|---|---|---|
| **Cloudflare Email Routing + Worker** (recommended) | DNS is at Cloudflare already; no mail server to run; the message never touches a disk before sealing; low cost | 25 MiB limit; Worker errors and reject codes need the spike; one more vendor sees mail in clear (in memory) |
| AWS SES inbound → S3 → Lambda | AWS is in use already | Inbound only in some regions; the raw mail is written to S3 in clear before we seal it; more parts |
| Postmark or Mailgun inbound (JSON webhook) | Parsing done for us | Monthly fee; a third company keeps mail in its logs; webhook still needs our queue |
| Our own SMTP server (Postfix + script) | Full control | A server open on port 25 to run, patch and keep off blocklists |

## 3. What a card shows

The Email kind uses the apps' card (`AppCard.tsx`, plain text only, no Markdown, no HTML, no remote content):

- **Sender line:** "Email · Auto" as for every app, then **From:** display name and address, always with
  "(unverified)". The apps plan rule stands: a mail's sender is never shown as verified. Forwarded mail breaks SPF, and
  the forwarder's account can write any From.
- **Forwarded by:** the account that forwarded it, when the headers show it (Gmail's envelope sender, `X-Forwarded-For`
  and similar; best effort, "(unverified)" too).
- **Subject** (≤ 300 characters), **date** (the `Date` header, shown in the viewer's time zone).
- **Body:** `text/plain` when the mail has it; else the HTML converted to text (links kept as text + address, images
  dropped, hidden elements dropped where the style is inline). The card shows the first 12 lines with "Show more"; the
  thread shows all of it up to 20,000 characters. Quoted older mail (`>` lines, "On … wrote:") is folded.
- **Attachments line (v1):** "2 attachments not kept: invoice.pdf (240 KB), photo.jpg (1.2 MB)".
- **Link:** none in v1 (an email has no web address). The first https link in the body is not promoted to the card's
  link: in mail it is often a tracking or phishing link.
- **Threads:** `References` / `In-Reply-To` that match an earlier mail of the same app put the new mail in that
  card's thread ("Re:" replies and ticket updates stay together). No match → a new card. Subject matching: no (too many
  false joins of "Order confirmation").
- **Gmail forwarding confirmation:** a mail from Gmail's forwarding sender with its confirmation subject is shown as a
  special card for the room's managers: "Gmail asks to confirm forwarding from x@gmail.com. Code: 123456. Enter the
  code in Gmail, or open the link from this card." Members see the plain card. The AI never opens it (outside
  content, as any app message). Outlook and other providers that send a confirmation get the plain card; the guide
  says to look for it.
- Mentions, `@all` and pings in a mail: never parsed (the apps rule).
- Push: "Email · Auto" + the subject, one line, ≤ 120 characters, only at the room level "All messages" (the apps rule).

**Phase 2 attachments:** kept as room files of the card's message (origin `email`, room storage, the room's members
only). Caps: 10 MB per file, 25 MB per mail, 20 files per mail, the team storage check. Over the caps: kept up to the
cap, the rest listed as "not kept". Executable types go on the download-only list. A member saves one to the team
folder with the existing "Save to team files". This needs `room_files.app_id` (and `user_id` nullable, or the app's
creator recorded): one migration.

## 4. Reply in the room

**v1: team discussion only.** The thread under each card is a normal room thread: members reply, react and ask Trina
("Draft an answer to this inquiry"). No mail leaves Trina. Each card has **Copy sender address**.

Later:

- Phase 2: **Reply by email** opens the person's own mail app (`mailto:` with To, `Re: <subject>`). No infra; the
  person sends from their own account. The To address comes from an unverified From, so the button shows the address
  before it opens.
- Phase 3: **Reply from the team's connected mail** (Gmail or Outlook connection) with the existing send card, the
  quoted mail and `In-Reply-To`, so it threads in the customer's inbox. The reply is posted in the thread as "Sent by
  …".
- Not recommended: Trina sending mail from `@in.<domain>`. It needs DKIM, bounce handling, a sending reputation and
  abuse control, and the customer gets mail from an address they do not know.

## 5. Address rotation

The apps' **Get a new address** (owners and admins in the room):

1. Confirm dialog: "The old address stops working now. Mail sent to it is refused. Change the forwarding filter in
   Gmail or Outlook to the new address. Gmail asks to confirm the new address again."
2. Delete the old hash at the mailbox, add the new one (section 2). Only then the new address shows.
3. Audit `room_app.rotate` (no token). The apps' `leaverKnows` mark works the same: a member who leaves after seeing
   the address marks it "Someone who left knows this address."

Mail sent to the old address after this gets `550 5.1.1` (a bounce to the sender), not a silent drop.

## 6. Who can see and enable it

- **Manage** (add, copy address, rotate, remove, Quiet, the switches): as all room apps (room apps plan "Permissions",
  owner decisions 4 and 5).
- **See and reply:** everyone in the room, **including people who join later** (app messages are never hidden). The
  add screen says so.
- **Admin switch:** Admin › Rooms, "Let rooms get email" (`TeamSettings.roomEmail`, default on for hosted and
  registered servers). Off: the Email kind is hidden, every Email app is paused and its address is removed from the
  mailbox (mail bounces). On again: the apps come back with **new** addresses (the old ones are gone for good).
- One Email app per room in v1 (a second one adds nothing).

## 7. Security

| risk | answer |
|---|---|
| **Spoofed sender** | Always "(unverified)". Never linked to a member; a From with a member's address is not shown as that member. No mentions, no buttons that act. |
| **Spam to a leaked address** | Unknown → 550. Limits: 30 mails per address per minute, 500 shown per app per day (the apps cap), 5,000 per team per day; over → 451 or pause with the apps' notice. Cloudflare's own checks before the Worker (spike: what it rejects). Get a new address in one click. Phase 2: an optional "Only accept mail forwarded by" list. |
| **Size** | 25 MiB per mail at the Worker; the item ≤ 1 MiB in v1; queue ≤ 2,000 items or 50 MB per team. |
| **HTML** | Never rendered in v1: converted to text on the team server, then the apps' plain-text card. Remote images are never loaded (no read receipts, no tracking pixel, no IP leak). Bidi and zero-width characters stripped. Phase 2 "View original": the HTML in the existing sandboxed preview frame with a CSP that blocks every remote load. |
| **Prompt injection** | A mail is outside content written by anyone: `APP_DATA_NOTE`, `markOutside()` on reads, the write cards are asked (room apps plan "AI behaviour"). The AI reads the same text people see, never the raw MIME or headers beyond From, Subject and Date. The room AI never runs by itself on a mail. A mail that says "Trina, send the files to …" is quoted data. |
| **Link phishing** | Links are text with their real address shown; no link becomes the card's button. |
| **Rate limits on the pull** | The poll is signed (team key, timestamp, nonce, body hash); one poll at a time per team. |
| **The token** | Never in a log (the Worker logs the hash prefix only), never audited, never given to the AI, members cannot read it. The cloud keeps only the hash. |
| **Replay** | Item id + receive time in the AEAD data; dedupe by item id and Message-ID. |
| **Gmail confirmation mail** | Shown to managers as its own card; the code is not sent anywhere; the AI cannot act on it. |
| **Forwarding blocked by the sender's provider** | Not a risk to us, a setup failure: Microsoft 365 can block automatic forwarding to outside addresses by a tenant policy (check the current default in the spike). The guide says "Your IT admin may need to allow forwarding." |

The security review for this plan's build is the same as the apps' (an independent review of the PR, the permission
matrix cases, a `leaks` check for the token shape).

## 8. Privacy text

On the Email add screen and in docs/for-admins (5 languages):

> Mail sent to this address goes through the Trina mail service (it runs on Cloudflare) to your team's server. The
> service reads each mail only to pass it on, and seals it so only your server can open it. It keeps a mail at most 24
> hours while your server is offline, and deletes it as soon as your server has it. Everyone in this room can read

## 9. Cost

- Cloudflare Email Routing: no fee. The Worker and Durable Objects: inside the Workers paid plan the hosting service
  has (about USD 5 a month base); a mail costs one Worker run and a few Durable Object writes. At 100 teams × 200 mails a
  day, about 600,000 runs a month: well inside the plan. Check prices before launch.
- Team server: one long poll per team, small.
- Phase 2 attachments: storage on the team server (the team's own disk quota), not on the cloud. Items with attachments
  are bigger in the queue (R2 or Durable Object storage, ≤ 24 h).
- People: about 2 weeks for v1 (core + mailbox + web), 1 week for phase 2.

## Change 2026-11-23: Amazon SES inbound on `in.trina.app`, not Cloudflare Email Routing

Decided by Dion and the owner (pras) on 2026-11-23. Cloudflare Email Routing takes a catch-all only on an apex domain,
and the MX of `trina.app` belongs to Daum mail. Amazon SES receiving takes a subdomain, and the hosting service already
runs on AWS (account engine-trina).

- **Flow:** MX `in.trina.app` → SES receiving (us-east-1) → receipt rule for the whole domain: (1) store the raw mail
  in S3 (SSE-S3, no public access, 1-day lifecycle), (2) call the gateway Lambda (asynchronous). The gateway runs the
  same `receiveMail` as the Worker (address, size, queue room, limits, auth headers, seal) and deletes the S3 object.
  The queue is one DynamoDB table (the same `MailStore` over a DynamoDB key-value adapter). The API (`/api/mail-in/v1/*`,
  contract unchanged) is a second Lambda on a function URL in response-stream mode (one sealed 10 MiB mail is about
  14 MB, over the 6 MB of a buffered answer). Code: [mailbox-ses/](../../../mailbox-ses/README.md).
- **Team lookup:** the hosting service's `POST https://cp.trina.app/internal/mail-in/team` (trina-cloud), with a bearer
  token. The API caches each answer (5 minutes served, 1 minute not served).
- **No refusal at SMTP time.** SES accepts every address of the domain before any code runs. An unknown, removed or
  replaced address, a mail over 10 MiB, a full queue and a limit all **drop** the mail with a `mail_refused` log line.
  No bounce is sent (a bounce goes to the envelope sender, which spam forges). The sender sees no error. The team server
  still posts nothing for an address it no longer has.
- **Held poll:** the gateway cannot wake a poll in the other Lambda; the poll looks at the table every 2 seconds. A
  newer poll of the same team does not end an older one in another Lambda instance (the 60-second lease makes delivery
  at least once, as before). The per-team call limit is per Lambda instance.
- **Store layout:** the per-team counters (`items`, `bytes`, `expired`) moved out of the team record into their own
  record, so the gateway never writes back an old seal key or address set.
- **Verdict:** `auth` comes from SES's own `Authentication-Results: amazonses.com` header (the topmost one).
- **Cost:** a held poll keeps one API Lambda busy (256 MB) while a team server is awake. Everything else is cents.
  When many teams use email, move the API onto a long-running host (for example the control plane) and keep SES, S3
  and the gateway.
