## Findings (what the stand-in hit)

- F3's stand-in was a **team** remote MCP connection (`write rule: ask`, `create_app` readOnly false, destructive false).
  Batch 4 (#404, docs/decisions/20261122-connector-always-allow.md) asks every time in a shared chat for "a change at a
  team connection's service" and keeps Always for a change on the person's **own** connection (`sharedAlwaysKey`:
  `row.scope === 'personal'`). So the stand-in got exactly the team rule.
- The owner's real case (Aside's Repl: an app on the person's own computer, a personal connection) already takes the
  personal path: shared card + repl card with Always for good, code behind "자세히" (`c-local-apps-always.test.ts`).
  A personal remote MCP connection takes the same Always path (`b-shared-chat-connections.test.ts`).
- What the team path still lacks: plain words. Its card keeps the call's raw JSON open (the `hidden` flag is set only
  for an app's code, `sent.runs`), and nothing says why there is no Always.
- Team-connection writes in a shared chat: the per-call ask stays (Rule A keeps a person's own choice final; a team
  account's service is shared by everyone and holds other people's things, and the chat's other people's words steer
  the call). It is only for writes through a team account; reads, the person's own connections and private chats keep
  Always.
- F5: share_folder refuses in a chat with other people's words unless the asker's own **message** names the folder and
  every person (M9 guards), also where its own card will show the folder and people anyway. An answer on the AI's
  question card is not that message, so every answer loops. share_with_person and post_to_room already dropped those
  guards outside a guest's chat (#403 B4); share_folder kept them for people without Always.
- F11: `promo_video` takes pictures only from a brand folder (spec.ts `inBrandFolder`), so the AI copied the photo the
  person attached in the chat (`chat:files/…`) to `shared/브랜드/images/` (a 16-person card). The MP4 is made only on a
  macOS development server (render.ts `mp4Available`; the Linux render is handed to the srt image, DECISIONS "V"), so
  on the Linux QA box nobody, the asker included, gets a download. On a Mac a shared viewer already may download it
  when they can open every picture (render.ts rowFor).
- Schedules: `scheduleCard` says "cannot open" whenever the server's exit address is unknown (`egressOf(ctx).known`),
  but url-gate ①d opens a plain address in the person's own scheduled run under their "Allow all websites".
- Notices: `noteSharedAnswer` gives the others only the unread number (kind 'answer', never pushed), also for a
  scheduled run's answer, whose asker is not watching; runtime.ts skips the scheduled run's message by design.

## Scope

In:
1. F3: a change card in a shared chat on a team connection says in plain words what happens and why it asks each time
   ("팀 연결이라…매번 물어봐요"); the call's values, code and JSON go behind "자세히" for every call that reaches nobody
   else (`Sent.ownAct`), not only an app's code. A call that reaches other people keeps send and its recipients in view
   (unchanged).
2. F5: share_folder keeps its "the asker's own message names it" guards only where a guest is among the people (as
   share_with_person and post_to_room since B4); elsewhere its own card (folder, people, Always) is the check, so an
   answer on the AI's question goes straight to one card. Tool words tell the AI to call share_folder with what the
   person answered, not to ask them to retype it.
3. F11: `promo_video` also takes a picture from this chat's files (`chat:files/…`: everyone in the chat sees it
   already), put into the video page as the picture itself (data: address, capped), so the AI never copies it to a team
   folder; the tool words say so. A shared viewer's play and MP4 do not need a team-path check for such a picture.
4. Schedules: the card says the address opens when the person's own "Allow all websites" is on (as the run will), and
   the remaining "cannot open" line names the way out in plain words instead of "공인 주소".
5. Notices: a scheduled run's finished answer in a shared chat or a project's shared chat tells the others as a main
   message does (kind 'message': unread number, push, desktop ring), by the task's owner.
