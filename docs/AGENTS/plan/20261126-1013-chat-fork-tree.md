## Goal

The team looked at the Claude desktop app's session list: a fork sits indented under the chat it came from, a fork can
be forked again, and the row's menu has "Fork" and "Detach to top level". The owner's team chat: "then we can fork from
forked session too? like a tree?" and "we can make forked session become root".

Today (#641) only a shared chat's title menu forks ("나만 보는 채팅에서 이어 하기"), and the fork is one more flat row in
the history with a "‘제목’에서 이어 왔어요" line in the chat. After this change:

- any chat I can write in forks, from the chat title's "···" and from its row's "···" in the history;
- forks show under their chat in the history, with an arrow that folds them;
- "최상위로 꺼내기" / "Detach to top level" makes a fork a top-level row again;
- deleting or hiding a chat never takes its forks: they move up one level.

This replaces #641's decision 1 (entry point A: only the shared chat's title menu). #641's decisions 2 and 3 stay.

## What a fork is (unchanged from #641 unless said)

| Source | Who may fork | What is copied | Where the fork goes |
|---|---|---|---|
| A shared chat (project, or shared with people) | as #641 (anyone who may open it, the guest gate) | as #641: what I see now, others' names kept, a hidden answer one line, others' notes only as the shared chat gives them to me, chat files by reference | as #641 |
| My own chat that only I see (in a project or not) | me | everything on the branch: every finished message, its steps, notes, files, attachments as they are (a chat file of a fork's copy keeps the chat that holds it, `fromChat`); my own session of the branch (Claude Code) | the same place (the same project, or none) |
| A fork (a chat of mine that holds copies) | me | as the row above: the copies stay copies (`fork_copy`, `withheld_copy`, `fromChat` pointing at the chat that keeps the file, the copied marks) | the same place |

Refused as in #641: safe operations (`safe_ops`), a room's side chat, a scheduled run (`fork_not_here`), nothing
finished on the branch yet (`fork_nothing`), a chat in the trash (404). Another person's private chat: 404 (as every
chat route). `fork_not_shared` goes away: a chat of one person now forks.

The server code is #641's `forkChat`, which already reads every message through `ChatStore.toMessage` with my view
(`messageView`) and copies `ownSessionOn` (works for any chat: every stash writes `turns.engine_session_blob`). For a
source that is not shared the audience is me alone, so `othersNotesFor`, `answerHiddenFrom` and the attachment view
give back what is there. The only changes in `forkChat`: the `!a.shared` refusal becomes "a chat that is not shared
must be mine", and the new row gets `fork_parent = <source id>`.

The fork's first answer (turn.ts `fork_pending`, #641) is unchanged: it resumes my own session of the branch with the
checks for me alone, else starts fresh from the copied words. `forkNote` (prompt.ts) gets one variant: a fork of a chat
that was not shared says "This chat is a fork of ‹name›'s chat ‘‹title›’ …, the original goes on without it" and
never "your instructions were written for that shared chat" (the source is read at the turn: `isSharedRow` of
`fork_of`, or `forkHoldsOthers` when it is gone).

## The tree

### Data: a parent of its own (migration 460)

`chats.fork_of` stays what it is in #641: where the copy came from (the "이어 왔어요" line, `forkCopiesOnly`,
`forkFirst` in turn.ts). The tree needs a second, movable pointer:

- `chats.fork_parent TEXT` (the chat this one sits under in my list; NULL: a top-level row) and an index on it.
- Backfill: `UPDATE chats SET fork_parent = fork_of WHERE fork_of IS NOT NULL` (forks #641 made before this change sit
  under their chat too).
- Additive, `min_compatible_reader: 1`: an older build ignores it.
- Number: dev's highest is 454; 455-459 are held by open PRs (#586, #631/#634, #636, #638, #641 = 459), so 460. Checked
  again before the PR.

Kept apart from `fork_of` because detaching changes only where the row sits (see "Detach"), and because a purged
parent re-points its children to its own parent (below) while `fork_of` must keep pointing at where the words came from.

### What the client gets

`Chat.forkParents?: Uuid7[]`: the chat's ancestors by `fork_parent`, nearest first, at most 8, for the chat's own
person only (`viewer === r.user_id`, in `chatOut` like `forkedFrom`). One small recursive query per fork row; nothing
for a chat that is no fork. Only ids, of chats this person once could open; never sent to anyone else (a fork its
person shared later: the others get no `forkParents`).

### One rule in the list: nearest ancestor in the same list

A row sits under the nearest of its `forkParents` that is a row of **the same list** (the same date-grouped history, or
the same section of mine). If none is, it is a top-level row there. This one rule covers every case without more
server state:

- **parent deleted** (it is in 삭제한 기록, not in the list): its forks go under its parent, or to the top. Restored, it
  takes them back. When the trash is emptied, `purgeChat` first re-points the chat's children
  (`UPDATE chats SET fork_parent = <its fork_parent> WHERE fork_parent = <it>`), so the chain stays whole;
- **parent hidden** (Hide from my list, a chat shared with me) or **no longer mine to open** (left the project, left
  the chat): it is not in my list, the same;
- **parent pinned**: pinned rows are a flat list of their own (pins are a choice per chat), so its forks show under the
  nearest ancestor in the history, or at the top;
- **sections**: a section is its own list. A fork in the same section as its chat sits under it; moving a chat to a
  section moves only that chat (as today), its forks stay where they are;
- **a filter** (Waiting, Last activity, Status): only rows the filter shows count;
- **not loaded yet** (the list is paged): top-level until "더 보기" brings the parent, which then appears right above it
  (the tree sits where its newest row is, next item).

Group by Project (chosen by hand, capped at three rows per project) stays flat in this change: its caps count rows,
and a tree there needs its own cap rules. Said in the decision file; can come from use.

### Order and dates

- A tree takes the place of its **newest row** by the list's sort (Last activity; Date created; by Title the top row's
  title). So a fork I worked in today brings its parent into Today, directly above it, as the Claude app keeps a
  session's forks together. Inside a tree, children newest first (or by title).
- With Group by Date the tree sits in its newest row's date; a date group's count and its folded mark count every row
  of it.

### Indent, the arrow, folding

- Indent 16 px per level, at most **2 levels**; deeper forks sit at the second level (each still under its own parent
  in order; the arrow of a level-2 row folds its own subtree).
- A row with forks under it has an arrow (ChevronRight, turned down when open) in its own left space, a separate button
  beside the row's link (never inside it): 20 px wide and the row's height on a computer, 24 px wide and the row's 48 px
  height on a phone (WCAG 2.2 target size). Its name: "‹title› 포크 접기 / 펼치기" ("Hide forks of ‹title›" / "Show
  forks of ‹title›"), `aria-expanded`. A row with an arrow starts its title after it (8 px further than a plain row:
  accepted, the owner's "a few mm doesn't matter").
- Open by default. Folded is kept with my folds (`tree:<chatId>` in prefs.folds, as the date groups' folds), so it is
  the same on every device.
- Folded, the row shows the count of the forks under it (small, grey, as a folded date shows its count) and the
  strongest session marker of itself and every fork under it ("?" first), so a fork that waits on me is never hidden.
  The chat on screen stays drawn under a folded parent (as a folded date does).
- Rows of a tree are `role` list items in nested order; the arrow's `aria-controls` is not used (the children are
  sibling `li`s): `aria-expanded` plus the label say it. Keyboard: Tab reaches the arrow before the row's link.

### Phone at 390

The same tree in the ☰ drawer and the 트리나 tab: 16 px per level, at most 2 levels (32 px at most in a 390 px row),
the 24 × 48 px arrow, the same count and marker when folded. The long-press sheet holds Fork and Detach like the "···".
No swipe, no separate screen.

## Entry points and words

- Title "···" (ChatTitleMenu) and the row's "···" (chatMenuItems: the Trina panel, the drawer, a project page's list).
- A chat that is not shared: **"포크" / "Fork"** (icon GitFork), after Rename. It opens the new fork with an empty box.
- A shared chat: **keeps "나만 보는 채팅에서 이어 하기" / "Continue in a chat only you see"**, now in the row's "···" too.
  Not unified, because (1) it says the one thing that matters there, that the copy is only mine (a fork of a shared
  chat changes who sees it; a fork of my own chat changes nothing about that, so "Fork" says it all), (2) the AI quotes
  this label to people when they ask for a personal tool in a shared chat (prompt.ts `privatelyMenu`), (3) it is the
  wording #641 shipped with the owner's OK.
- **"최상위로 꺼내기" / "Detach to top level"**: in both menus of a fork that has a parent (`forkParents` not empty), for
  its person. `PATCH /api/chats/:id { forkParent: null }` (UpdateChatBody, only null is accepted; the chat's person
  only, 404 otherwise as PATCH's other fields; a shared chat's creator too). It sets `fork_parent = NULL`, publishes
  `chat.updated`, audited `chat.fork_detach`. Its own forks stay under it.
- The "이어 왔어요" line **stays** after Detach: it is where the words came from (a fact about the chat, kept with its
  link while I may open the source), while Detach is about where the row sits in my list, as in the Claude app. Nothing
  re-attaches (no "move under"); a new fork is the way to make a new child.
- The fork's title is the source's, as #641 (the indent and the line tell them apart; renaming is one menu item away).

Four new strings in six locales (en, ko, ja, zh, es, id): chat.fork, chat.forkDetach, chat.forkShow, chat.forkHide;
the forkNote variant is English (the AI's). Error texts reuse #641's (`forkNotHere`, `forkNothingYet`).

## Decisions (no owner decision open; two calls taken with a recommendation, the reviewer to confirm)

1. **Where a tree sits by date.** A: at its newest row (a fork used today brings its parent into Today, right above it).
   B: at the parent's date (the fork you just used may be far down, in "Older", under an old parent). **Recommend A**:
   the Claude app keeps a session's forks together, and B hides the chat you are working in.
2. **Folded or open by default.** A: open. B: folded (only the parent shows). **Recommend A**: a new fork must be seen
   right where it was made; folding is one click and kept per person.

## Review

the kept shared-chat label and Detach keeping the line: agreed).

1. A fork of my own chat (or of a fork) would never resume: the shared-chat resume path needs answer records, which
   only shared chats have, and the first answer then deleted the copied session. Now such a fork resumes on the plain
   path (`chat.engine_session_leaf_id` = the copied leaf, `stashWrittenBy` where others' words are in it), the checks for
   the person still run, and the skill list is recorded; tests prove `resumed=true` for both.
2. `forkParents` could name another person's private chat (a fork they shared later, forked by me). The chain now walks
   only through my own chats plus the first one that is not mine.
3. My uploads in a fork of my own chat would break when the original is purged (`attachments.chat_id` cascades). The
   fork now copies my own upload rows (same file, new id, own thumbnail file); a test purges the original and sends again.
4. Trees are built over the whole list before the date split (DateGroups), each date's count and mark per tree.
