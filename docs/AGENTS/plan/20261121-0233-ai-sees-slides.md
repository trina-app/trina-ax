# The AI sees PowerPoint slides as images (read pages + as_images on a .pptx)

- Date (UTC): 2026-11-21 02:33
- Branch: `feat/ai-sees-slides`
- Status: done
- Where: server/src/files (read), server/src/chat (room_file), shared/src/tools.ts (descriptions). Why: the read path
  and its tools live there (docs/REPOSITORY-RULES.md)
- Version impact: minor (a new capability of read, chat_file and room_file: slides as images)

## Goal

The owner: "ppt 슬라이드를 못봐?? 이거 보게 바로 해야할듯". Today `read` gives a .pptx as text only and refuses
`pages` / `as_images` ("only for PDF files"), so the AI cannot tell what a slide looks like (layout, pictures, overlaps,
text running out of its box). Claude Code can look at a slide picture; Trina's AI should too. After this, `read` with
`pages` (slide numbers) or `as_images` on a .pptx shows each slide as an image with its text, the way a PDF's pages
come; chat_file and room_file the same. A plain read of a deck stays text, as before.

## Renderer

Options:

1. **The server's own deck drawing, already shipped** (files/pptx-html.ts in the isolated office worker, printed by the
   pinned headless browser in files/html-pdf.ts; docs/decisions/20261116-pptx-to-pdf.md, make_file's PDF of a deck),
   then the existing PDF page-image path (pdftoppm / PDFKit, files/vision.ts). No new package: the browser is
   already in the one list (`browser` group, chrome-headless-shell artifact) and installed on the image, Linux
   servers, the dev environment and the office Mac. Same isolation as every untrusted-file converter (office worker:
   no network, time and memory limits; the print: bwrap / sandbox-exec, no network, cgroup memory, temp work dir).
   Not drawn: charts, SmartArt, EMF/WMF pictures (a grey box), shadows, gradients; the AI is told which.
2. LibreOffice headless → PDF: faithful charts and SmartArt, but 300-500 MB in every image and Mac bundle, a large
   untrusted-input surface and its own sandbox and font work. The decision of 2026-11-16 already turned it down; it
   is over this task's 200 MB line.

Chosen: 1. Charts are the main gap; their data is in the deck's text read already. Drawing charts in pptx-html.ts is
a follow-up.

## Scope

In:
- `read` on a .pptx with `pages` and/or `as_images`: the deck drawn with **every** slide (hidden ones too, so page N
  is slide N as PowerPoint numbers them; a hidden slide is marked), printed to a PDF, and the PDF's pages given by the
  existing `pdfPagesForModel` with images on. Same rules as a PDF: at most 20 pages per call, `pages` required over 10
  slides, the per-turn image budget, the team's image switch and the engine check.
- The PDF kept in memory by the deck's sha256 (a small LRU, bytes capped), so reading slides 1-5 and then 6-10 draws
  the deck once. Concurrent reads of one deck share one drawing.
- room_file (chat turn) and chat_file the same (chat_file goes through read).
- A plain message when this server cannot draw slides (no headless browser, no isolation, too little memory): the
  text read still works, and the message says so.
- Tool descriptions: slides can be seen as images.
- make_file's PDF of a deck uses the same drawing helper (one code path; hidden slides stay out there).

Out (follow-ups):
- .ppt (old binary) and .odp: the drawing reads only Office Open XML. A plain refusal names .pptx.
- Word, Excel and Hangul pages as images: no converter on the server draws them (pandoc has no faithful docx → PDF,
  nothing renders xlsx or hwp pages). Would need LibreOffice or a renderer of their own.
- Charts and SmartArt drawn in slides.

## Steps

1. pptx-html.ts: an option to draw hidden slides too (marked), a worker mode `pptx-slides` for it.
2. files/deck-pdf.ts: deck bytes → PDF through the office worker and the headless browser, the render slot, the
   memory cache by sha256, in-flight sharing, errors as plain ToolErrors.
3. service.ts read: a .pptx with pages / as_images goes to a small `readDeck` (auth, bound bytes, quarantine,
   deckPdf, pdfLayer, pdfPagesForModel with images). The refusal for other formats names PDF and PowerPoint.
4. room-tools.ts: a .pptx with pages / as_images (chat turn) → deckPdf → the room PDF path.
5. make-file.ts fromDeck uses deckPdf.
6. Descriptions in shared/src/tools.ts, room-tools.ts, chat-file-tool.ts.
7. Tests, changes/ file, decision file.
8. QA on a private copy of the local QA team with a real engine: a multi-slide deck with pictures and a chart, asked
   "슬라이드 3번에 뭐가 보여? 레이아웃 이상한 데 있어?" before and after.

docs/decisions/20261121-ai-sees-slides.md (extends 20261116-pptx-to-pdf.md: the same drawing serves read). No new

## Risks

- Another branch (fix/ai-sees-and-saves-workspace-output) changes read in service.ts for work-folder paths: this change
  touches only the format dispatch line and adds one method, to keep conflicts small.
- Memory: the cache holds at most a few PDFs (capped bytes); a deck's PDF is dropped on eviction.
- Security: the deck is untrusted; drawing runs only in the office worker and the isolated browser, as for make_file.
  The cache is keyed by content hash and is only reached after the caller's own read check of those bytes.
- No migration, no UI, no new strings in the app languages.

## Tests

`bun run typecheck`, `bun run check:docs`, `bun run check:prepush`, unit tests: pptx-html hidden-slide option, deckPdf
cache and in-flight sharing, read of a .pptx with pages / as_images (images, page range, 20-page rule, pages required
over 10), refusal when the browser is missing, .ppt refused plainly, room_file deck pages, existing make_file pptx-pdf
and vision-read tests.

## Result

Built as planned, no new package. read / chat_file / room_file draw a .pptx with every slide (files/deck-pdf.ts, worker
mode `pptx-slides`) and give it as PDF pages with pictures; the PDF is cached in memory by sha256. make_file's PDF of a
deck uses the same helper. QA on a private copy of the local QA team with a real API engine (OpenRouter, Claude Sonnet
5.5), "슬라이드 3번에 뭐가 보여? 레이아웃 이상한 데 있어?" on a 5-slide deck with a photo and a chart:
- before (dev): read text → read pages refused ("only for PDF files") → make_file saved an extra PDF in the person's
  folder → read that PDF's page 3. Four calls and a file nobody asked for.
- after: one read (`slides 3 of 5, 1 image`), no file saved; the answer named the caption over the photo, the text cut
  off at the right edge and the empty bottom, and said the grey box is the chart, not a fault.
