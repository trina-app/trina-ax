- Date (UTC): 2026-11-23 16:54, revised after the owner's "루트를 고쳐야 한다"

- Status: done for PR 1 (PDF and preview follow in their own PRs)
- Where: Team AX core (`server/src/files`, `server/src/tools`, `shared/src/tools.ts`, `web/src`). Why: document editors, tools and preview are core (docs/REPOSITORY-RULES.md)

## Goal

A seal or signature lands on the mark of the right signer in .docx, .hwp, .hwpx and PDF, or the tool says it did not.
Today, in real runs on Word, 2 of 4 seals landed about 10 mm off and the tool reported success (QA TC-8357).

## Root cause (checked in the code, corrected after review)

1. The target is the AI's free text. Word centres on whatever it was given, so a whole line moves the seal.
2. Each format places differently. Word estimates text width and assumes a 1.2 line height. HWP has the renderer's
   layout, but a label inside a run is still estimated from character shares. PDF has only corners or x/y.
3. A saved result carries no evidence of where the picture landed. The results do say layout is unchecked, so the defect
   is missing evidence, not a false claim of a check.

## What each format can measure

| Format | Position | Landing evidence |
|---|---|---|
| .hwp, .hwpx | rhwp render tree, with `Image` boxes | new Image box against the mark in the layout before placing. rhwp is not Hangul (other fonts, known row and line differences), so this is "checked in the preview engine", never "verified", and it never moves a picture |
| PDF | to prototype: `pdftotext -bbox` (Poppler is on every install), all four rotations and CropBox | after the last operation; a mark that cannot be measured is reported as such |
| .docx | no layout engine on servers | CI asserts the saved XML. LibreOffice and Word readings are recorded by hand. The result says "tied to the mark, not rendered" |

## Design, after the independent review (verdict: rework)

Dropped: public slot ids (they shift with fill and added rows, and read order differs from editor order), the read note
(it misses chat files, guests and second documents, and would raise document text into a server-voice note), selecting
by a person's name (a seal could go on someone else's mark with no human check), and automatic correction on HWP (it
could move a seal that is right in Hancom).

1. **One resolver, `server/src/files/sign-slots.ts`.** Marks, signature lines and label cells, resolved on the exact
   bytes being edited, after same-call fills. Input stays the existing text plus `occurrence`. One candidate: use it.
   Several: refuse and list them as capped, JSON-quoted document text with control and bidi characters removed and
   hidden text excluded. A same-call edit that changes the candidate list is refused.
2. **Aim.** The seal is centred on the aim range ("인" of "서명 또는 인"). Tolerance: 2 mm per axis from the aim's centre.
3. **Word.** Anchor on the aim's character. Real Word is not available to test `wp:align`, so the offset stays and reads
   `w:spacing`. Fill and stamp in one `w:t` become one splice.
4. **Order per tool.** `edit_office` and chat `edit_pdf` ask the card before the worker, so a read-only resolve runs before
   their card: nobody approves a call that is then refused. Card order and rules do not change.
5. **Result text.** Quotes the text it landed on and one state: `checked in the preview engine`, `not checked` (engine
   busy or no measure), or `tied to the mark, not rendered`. A measured miss on PDF or HWP saves nothing.

## Regression corpus

Made-up forms per format: whole-line label, 갑/을 on one line, marks in table cells, long wrapping lines, fill plus added
rows, fill and stamp in one run, multi-page, (서명 또는 인), exact line spacing, no mark. HWP and PDF assert the distance
from the aim numerically; Word asserts the XML in CI. The two public government forms are run locally and in Hancom Docs,
never committed.

## Risks

A HWP check adds a layout job (15 s wait, 20 s run, one per server): a busy engine reports "not checked" and does not
block. Existing PDF corner and x/y calls must not change.
