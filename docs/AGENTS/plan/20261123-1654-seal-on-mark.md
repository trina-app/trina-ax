# One signing path: a seal goes on a slot found in the document, and the landing is checked

- Date (UTC): 2026-11-23 16:54, revised after the owner's "루트를 고쳐야 한다"
- Branch: `fix/seal-on-mark`
- Status: in progress (plan under review)
- Where: Team AX core (`server/src/files`, `server/src/tools`, `shared/src/tools.ts`, `web/src`). Why: document editors, tools and preview are core (docs/REPOSITORY-RULES.md)
- Version impact: patch or minor, decided at the end: minor if the tools gain the `slot` input (a new optional capability)

## Goal

A seal or signature lands on the mark of the right signer in .docx, .hwp, .hwpx and PDF, or the tool says it did not.
Today, in real runs on Word, 2 of 4 seals landed about 10 mm off and the tool reported success (QA TC-8357).

## Root cause (checked in the code)

1. The target is the AI's free text. Word centres on whatever it was given; a whole line moves the seal.
2. Each format places differently. Word estimates text width (`textWidthEmu`); HWP uses the renderer's layout but shares
   of a run for a label inside it; PDF has only corners or x/y that the AI must work out, though `pdf-text.ts` has glyphs.
3. Nothing checks the landing. Success means "the file was written and reads back".

## What each format can really measure (checked on this Mac and in `scripts/system/packages.json`)

| Format | Position source | Verify after placing |
|---|---|---|
| .hwp, .hwpx | rhwp render tree: text runs, cells, and `Image` nodes with a `bbox` (seen on a stamped government form) | re-run the layout on the saved bytes, compare the Image box with the mark's box |
| PDF | glyph positions (`pdf-text.ts`) | re-read the saved page: the image's matrix against the mark's glyph box |
| .docx | **no layout engine on servers**: LibreOffice is not in `packages.json`, only on dev Macs | structural: the anchor sits on the mark's first character in the saved XML, offset centred on the mark. The result says the position is tied to the mark and was not rendered |

Adding LibreOffice to every server is a size and security decision for the owner, so it is out of this PR and raised in
the report. In Word the anchor at the mark's own character leaves only half the mark's width as an estimate (about 1 mm
on "(인)") instead of a whole line's. The corpus measures this with LibreOffice where it is installed.

## Design

1. **`server/src/files/sign-slots.ts`, pure and shared.** Text to slots: marks (인, 印, 서명, 날인, 서명 또는 인, 서명 또는
   날인, Seal, Signature, L.S., spacing and full-width variants), signature lines (`____`, a label ending in `:` before
   them), and label cells (서명, 날인, Signature with an empty cell right or below). Each slot: id, kind, signer or role
   (the text before the mark back to the previous mark, or the row's label), page when known, aim range ("인" of "서명
   또는 인"). Ids are ordinal in reading order (`s1`, `s2`), computed from the file being edited, so a stale id cannot
   point at a moved mark without the signer check below.
2. **Showing slots to the AI, no new tool.** `read` of a .docx, .hwp, .hwpx or PDF that has slots gets one note listing
   them (the existing `file-notes` path). A refusal for an ambiguous target lists them too.
3. **Choosing a slot.** New optional `slot` on Word `insert_picture`, `edit_hwp` image changes, `stamp_pdf` and
   `stamp_image`: an id, or a signer's name or role. Free text (`over`, `at`) resolves to a slot through the same
   function. One slot: use it. Several: refuse and list them, unless `occurrence` picks one. None: today's behaviour for
   `over` and `at`; PDF corners and x/y stay as they are.
4. **Measure.** HWP: the mark's box from the layout, the aim from the run's measured edges. PDF: the glyph box.
   Word: the anchor at the mark's character.
5. **Verify, before anything is saved.** Off target by more than the tolerance (the picture's centre outside the mark's
   box grown by 2 mm): correct once from the measured difference, verify again, else refuse with nothing saved. Where the
   renderer differs from Hangul (no stored layout), the result states what was verified and what was not. The check runs
   before the existing card and save steps, whose order and rules do not change.
6. **Result text.** Names the slot, the signer and the text it landed on, and one of: `verified` (measured on the saved
   file), `tied to the mark, not rendered` (Word), `checked in the preview engine only` (HWP with no stored layout).
7. **Preview (TC-8358).** Cause is in our use of docx-preview: its zero-height box sits on the baseline and loses
   `relativeFrom`. Boxes of `relativeFrom="line"` pictures are aligned to the line's top; other floating pictures stay.

Untouched: the picture card, Always, ownership checks, size and format limits, the isolated workers.

## Regression corpus

`tests/lib/sign-corpus.ts` plus `tests/unit/sign-corpus.test.ts`, made-up forms in each format: whole-line label, 갑/을 on
one line, marks in table cells, long wrapping lines, fill plus added rows, multi-page, (서명 또는 인), no mark. Each asserts
numerically that the picture's centre is on the mark. The two public government forms are used locally and in the
Hancom check, never committed (the repository holds no third-party forms), with their expected numbers in the report.
