## Goal

The batch 3 smoke (b3s, 11-22) found:

1. A web page's "Restore this version" (ArtifactPanel, #379) runs at once with a toast only. The chat file panel's
   restore (#375) asks first, names who will see the change, writes the chat line "○○님이 <file>을(를) 버전 N(으)로
   되돌렸어요" and the others see it live. A page should do the same.
2. S-120: when the AI posts to a room for someone, members see an unread badge and nothing in Activity. Check it
   against a person's own room message and make them the same, by the room's notification setting, no extra noise.
3. S-110 (TC-b3s-23): "글자만 조금 키워줘" on a room banner in the ✦ side chat raised four cards: two "그림 파일을 만드는
   명령 실행: banner.png" cards for two commands that make the same picture in the chat's work folder, the copy card
   into the project, and a rename card for the copy this answer just made. Two of them are not needed (#381: one card
   per target in an answer; none for what the answer made itself), and the command card's words are developer words.
4. Small: a shared chat's add/remove lines and an added person's open page need a reload (TC-b3s-16); "버전 2을"
   (TC-b3s-17); step lines show `매출/**/*` (TC-b3s-8); the English side-chat room button.

## Scope

In:

1. **Page restore.** Before the restore: the chat file panel's confirm (title "Restore version N?", the body that says
   the current content stays a version, and in a chat others see "{names} will see the change in this chat"). After
   it: the server writes the chat line in `chat_file_events` (kind `restored`, the same table and reader as #375; a
   page's row has `file_id` `page:<new version id>`, so no migration and an older build skips it) and reads it with
   GET …/audience `events` as "{actor} restored {page title} to version {n}", only for a viewer who may see that
   version (the artifact's own hidden-version rule). The others' windows already get `artifact.updated`; the chat page
   reads its lines again when an artifact version arrives (`artifactsRev`), so the line shows live for everyone.
   Shared code: the confirm body and line words of #375 (FilePanel, ChatEventLine), one helper for the confirm.
2. **Room posts by the AI.** A test that an AI post (post_to_room, author = the person) and the same person's own
   message make the same room notices for every member at each level (all / mentions / off); fix only if they differ.
3. **Banner edit cards.** In one answer after a room read:
   - a dev-environment command whose output files (shellOutputs) are all files an earlier command of this answer was
     allowed to make, that removes, moves, installs and reaches the network nothing (the card's own checks), goes on
     without a second card (the yes covered that target; step "이번 답에서 허용한 작업이라 묻지 않음");
   - renaming (rename_file, same folder) a file this answer made and nobody changed since needs no card when the call
     that put it there was allowed in this answer (the copy card's yes): same file, same people;
   - the command card's words say what happens: "그림 파일 만들기: banner.png" (not "…을 만드는 명령 실행").
   The owner's 11-22 rule (docs/decisions/20261122-ask-less-side-chat-runs.md) stays: the first command after a room
   read still asks.
4. Small: the chat page reads its people lines again on every `chat.updated` of that chat and retries a "no longer
   shared" page when the chat comes back to it; Korean particles after numbers through the i18n particle marks
   (`{n}을(를)`, `{n}(으)로`); glob steps show the folder and file kind in words ("파일 찾기 · 매출 · .xlsx"); the
   English room button "Send to chat" (Korean "대화에 보내기").

Out: page slugs in step lines (`oct-sales-dashboard`), the PDF size note and the AI's preview sentence of TC-b3s-17,
versions for dev-box changes in the person's own folder (the owner's follow-up).

## Risks

- Security: fewer room cards after a room read. Only a later command with the same output names and none of the risky
  parts, after a yes in the same answer; only a same-folder rename of a file this answer made. Everything else keeps
  its card. Tests pin both and their limits.
- No migration (the page line reuses chat_file_events with a `page:` id; older builds skip unknown ids).
- Five app languages plus id for every new string; phone and desktop for the confirm.
