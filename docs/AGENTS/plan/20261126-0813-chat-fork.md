# Fork a chat: "Continue in a chat only you see" carries the conversation

- Date (UTC): 2026-11-26 08:13
- Branch: `plan/chat-fork` (plan only; the build goes on `feat/chat-fork`)
- Status: draft
- Where: server/src/chat (new `fork.ts`, turn.ts first-turn path, shared.ts), server/src/engine/claude.ts (args),
  server/src/routes/chats.ts (one route), one migration, web/src/pages/Chat.tsx + components/chat/privateAsk.ts,

- Version impact: minor (a new user-visible feature, one new API route, one additive migration; old clients unaffected)

## Goal

People ask whether a shared chat can be "forked". Today the shared chat's menu item **"나만 보는 채팅에서 이어 하기" /
"Continue in a chat only you see"** (ChatTitleMenu `chat-continue-privately` → Chat.tsx `askPrivately` /
`askPrivatelyHome`) opens an **empty** private chat with my last question typed in the box. No message, no file and
nothing the AI knew comes along, so the person explains everything again and the AI redoes its work (and the cache is
lost). The AI itself sends people to this item when it needs personal tools a shared chat does not have
(prompt.ts `privatelyMenu`), so the empty result hurts most exactly there.

After this change the same item makes a **real fork**: a new chat only I see, in the same place, that shows the
conversation up to now as I see it and whose AI goes on from my own engine session (Claude Code) or from the history
(Codex, API engine). Nothing changes for the others in the shared chat.

| ChatGPT | message ⋯ → "Branch in new chat" (web, 2025-09-04); a shared link's "continue" makes "a separate, private conversation in the recipient's account" | history up to that message, title "Branch …", original unchanged | the copied messages | shared links may carry images/files; memory and custom instructions not stated |
| ChatGPT group chats (retired 2026-07-09) | adding a person to a chat made **a copy** as the group chat, the original stayed private | copied | copied | — |
| Codex CLI | `codex fork` / `/fork` (interactive), `codex exec fork <id> [prompt]` | "preserving the original transcript", new thread id | the copied transcript | not stated (`--worktree` is separate) |
| Slack (Slackbot) / Notion AI | no fork found; "start a new conversation" / chat history only | — | — | — |

Takeaways: a fork copies **what the person already saw** into a separate chat of theirs and leaves the original alone
(Claude Code, ChatGPT shared-link continue, ChatGPT group-chat copy). Claude Code forks the model's full context, not a
summary; nobody copies files into the fork (claude.ai and Claude Code don't; ChatGPT only within what a share carries).

## Engine facts (measured on this Mac, 2026-11-26)

- Pinned Claude Code **2.1.305** (versions.json) has `--fork-session`, and it accepts our own id:
  `claude -p --resume <A> --fork-session --session-id <B>` wrote `<B>.jsonl` with every line's `sessionId` = B, left
  `<A>.jsonl` unchanged, and answered from A's context (asked to remember a word in A, the fork named it). Same on 2.1.332.
- Run from a **different working directory** (as a new Trina chat is), the fork's first request read 20,077 tokens from
  the cache and wrote 14,758 (the part after the working-directory announcement). So a fork's first turn costs about one
  cache write of the conversation, once; the same chat-to-chat fork from the same directory read it all from cache.
- 2.1.305 also has the hidden `--resume-session-at <message uuid>` (the SDK's `resumeSessionAt`). Not used in v1.
- Our launcher takes `sessionRestore.name` and `sessionCollect.name` separately (native/cmd/mycel-launcher/main.go), so
  restoring `<A>.jsonl` and collecting `<B>.jsonl` needs no launcher change; `engine/claude.ts` builds both from one
  `sessionId` today and gets a `forkFrom` input.
- Codex (pinned 0.163.0) has `codex exec fork`, but our Codex turns run `exec --ephemeral` and start fresh every turn
  with the branch history (engine/codex.ts); the API engine too. For them a fork is the copied history plus my own step
  records, which is what their next turn in the original would have had anyway.

## What a fork copies

1. **Visible history, up to the end of the branch I am on** (only finished messages; a running answer is not copied).
   Every message as I see it now (`rt.history(... { runner: me, withheld, everyone: true })` and the same
   AnswerSight the app uses): others' questions and answers keep their author; an answer hidden from me becomes the same
   one line I see (a copied row marked withheld, nothing of it copied). New message ids, the same parent chain; the
   copied rows keep `created_at` so the fork reads like the original.
2. **Steps and step notes:** the step list of each copied answer as I see it (`ChatStore.viewSteps` for me). Step notes
   (`messages.step_notes`, #409) only for **my own** answers: another person's notes are theirs alone today and stay so.
3. **Engine context.**
   - Claude Code, and I have my own session on this branch (`ownSessionOn`) that passes today's shared-resume checks
     (`sessionHeld`, the person can still open everything it holds): at fork time the server copies that stash file into
     the fork's session folder (a snapshot: the original may go on or drop it later). The fork's first turn restores it
     under its old id and runs `--resume <old> --fork-session --session-id <new>`; from then on the fork resumes `<new>`
     like any private chat. What others wrote after my last answer, up to the fork point, comes with that first message
     in `<since_your_last_answer>`, exactly as a resume in the shared chat would send it.
   - No usable own session (never answered here, a check fails, Codex, API engine, the session is too large or lost):
     the fork's first turn starts fresh from the copied history with the summary when it does not fit
     (history-summary.ts) and my own step records, as any fresh session does today. No new fallback code.
   - The first message after the fork tells the AI, in one line, that this is now a chat only this person sees, copied
     from the shared chat, and that personal tools (memories, personal connections, browser, schedules) are now there.
     The resumed session keeps its first system prompt (Claude Code records it), so this line and the tool set built
     for the private chat (the `refreshTools` path a card's connection already uses) carry the change.
4. **Attachments and files: references, not copies.** A copied message keeps its attachments pointing at the original
   chat's files (chat_files of the source chat, team files by path). They open while I may still open the original chat
   or the team file, as now (`seesChatFiles`, the team-file check); when I lose that, the card says the file is no longer
   available and `branchLostAttachment` (extended to source-chat files) drops the fork's session, as it does for a team
   file today. Nobody's file is duplicated into my space and no storage is used. Files the AI makes in the fork are the
   fork's own, as in any chat.
5. **Engine, model and effort:** the chat's engine and `model` are copied. Effort is not stored per chat on dev; if
   `feat/model-effort-choice` lands with a per-chat effort, copy it too (one line). A model the person may not use any
   more falls back as a new chat would.
6. **Marks that protect later actions** (copied as they are, never cleared): `session_tainted`, `others_words`,
   `room_outside`, the read scope (`addSources` of the source's scope) and the answer records of copied answers
   (`shared_answer_reads`, ids mapped). So remember protection, room cards and the "N answers used places <name> can't
   open" warning on a later Share of the fork work as in the original.

Not copied: pins, mute, threads under answers, schedules, the original's people or share, open cards (an unanswered
card in the original stays there), "allow for this session"-like grants (we have none: Always allow is per person
already).

- **Link back:** one line above the copied messages: "‹title›에서 이어 왔어요 / Continued from ‹title›", a link while I

  private chat exists (sharing model).

- **Phone:** the same title menu item (the phone layout already shows it) and the same line; the app is the web UI.

  the fork. Removed: the prefilled question.

## Steps

1. Migration (check the highest number in `server/migrations/` on dev first): `chats.fork_of TEXT`,
   `chats.fork_at TEXT` (source chat and message), `chats.fork_session TEXT` (the copied stash's old id, cleared by the
   first turn), `messages.withheld_copy INTEGER NOT NULL DEFAULT 0`. Additive (reader 1).
2. `server/src/chat/fork.ts`: `forkChat(rt, chatId, userId)` in one transaction: access check (`chatFor 'view'`, not
   confidential, not a side-room or room chat, not a schedule's run chat, the person may start a private chat in the
   target place), copy rows as in "What a fork copies", copy the stash file (outside the transaction, before commit;
   failure = no session, still a fork), audit `chat.fork`. Add the fork's pending stash to `SESSION_CHATS_OF` cleanup.
3. `POST /api/chats/:id/fork` → `201 { chat }`; 403/404 as the chat routes; 409 while nothing finished is on the branch.
   `docs:api` updated.
4. turn.ts first-turn path: `fork_session` set → resume-with-fork (engine/claude.ts `forkFrom`), since-block from the
   copied rows after my last own answer, the fork line, then clear `fork_session`. Same checks as a shared resume; a
   failure = fresh session.
5. Web: Chat.tsx `onPrivately` calls the route and navigates to the new chat; `privateAsk.ts` keeps the Home/project
   box path only as the error fallback. The "Continued from" line in Messages. Five languages (`check:i18n`).
6. docs/CONNECTIONS.md is not touched (no connection mode changes). A decision file
   `docs/decisions/<date>-chat-fork.md` with the owner's answers; `changes/chat-fork.md`.

## Decisions (owner, at most 3)

1. **Entry points.** A: only the existing title-menu item in shared chats, fork at the end of my branch, like Claude
   Code's `/branch`. B: A plus "여기서부터 새 채팅으로" in each answer's menu (ChatGPT's "Branch in new chat"), shared
   chats only. C: B in private chats too. **Recommend A.** No new button; private chats already have edit/regenerate
   branches for "try another way"; B/C can come later from use (the answer would start a fresh session or need
   `--resume-session-at`).
2. **Other people's words in my private copy.** A: copy everything I can see now, names kept; hidden answers stay one
   line; others' step notes never. B: only my own questions and answers plus a summary of the rest. C: ask the others.
   **Recommend A.** They are words I already see and could copy by hand; ChatGPT and Claude Code copy what the viewer
   saw; B would break the AI's context, C is friction the sharing model never asks for.
3. **When I later lose access to the original** (removed from the project, chat deleted). A: the copied words stay; the
   files follow the original's access (cards go unavailable, the fork's session is dropped and its next answer starts
   fresh from the words). B: everything stays (copy the files at fork time). C: the fork goes too. **Recommend A.**
   Files keep their owner's rules (as Drive shortcuts do) and no storage is doubled; the words are what I saw.

## Risks

- Privacy: the fork must never copy what I cannot see now (withheld answers, others' step notes, others' sessions). The
  copy reads through the same functions the app and the engine use for me; tests pin each case.
- A resumed shared-chat session keeps the shared chat's system prompt: the fork line and the rebuilt tool set must make
  personal tools usable on the first fork turn (QA: ask for a memory and a personal connection in the first message).
- Engine lockdown: a new flag on the engine command line → run tests/engine/lockdown-claude.ts (and the sub-agent one)
  before merging.
- Stash size: copying up to 40 MiB per fork; counted against storage like a session.
- Five languages, phone and desktop; the AI's quoted label stays the same.
