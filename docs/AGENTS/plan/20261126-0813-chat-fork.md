# Fork a chat: "Continue in a chat only you see" carries the conversation

- Date (UTC): 2026-11-26 08:13
- Branch: `plan/chat-fork` (plan only; the build goes on `feat/chat-fork`)
- Status: done
- Where: server/src/chat (new `fork.ts`, turn.ts first-turn path, shared.ts, store.ts/chat-files.ts source-chat references, prompt.ts),
  server/src/routes/chats.ts (one route), one migration, web/src/pages/Chat.tsx + components/chat/privateAsk.ts,
  i18n. Why: a chat behaviour of the server and its web app (docs/REPOSITORY-RULES.md)
- Version impact: minor (a new user-visible feature, one new API route, one additive migration; old clients unaffected)

## Goal

People ask whether a shared chat can be "forked". Today the shared chat's menu item **"나만 보는 채팅에서 이어 하기" /
"Continue in a chat only you see"** (ChatTitleMenu `chat-continue-privately` → Chat.tsx `askPrivately` /
`askPrivatelyHome`) opens an **empty** private chat with my last question typed in the box. No message, no file and
nothing the AI knew comes along, so the person explains everything again and the AI redoes its work (and the cache is
lost). The AI itself sends people to this item when it needs personal tools a shared chat does not have
(prompt.ts `privatelyMenu`), so the empty result hurts most exactly there.

After this change the same item makes a **real fork**: a new chat only I see, in the same place, that shows the
conversation up to now as I see it and whose AI goes on from my own engine session (Claude Code) or from the history
(Codex, API engine). Nothing changes for the others in the shared chat.

Takeaways: a fork copies **what the person already saw** into a separate chat of theirs and leaves the original alone
(Claude Code, ChatGPT shared-link continue, ChatGPT group-chat copy). Claude Code forks the model's full context, not a
summary; nobody copies files into the fork (claude.ai and Claude Code don't; ChatGPT only within what a share carries).

## Engine facts (measured on this Mac, 2026-11-26)

- Pinned Claude Code **2.1.305** (versions.json) has `--fork-session`, and it accepts our own id:
  `claude -p --resume <A> --fork-session --session-id <B>` wrote `<B>.jsonl` with every line's `sessionId` = B, left
  `<A>.jsonl` unchanged, and answered from A's context (asked to remember a word in A, the fork named it). Same on 2.1.332.
- Run from a **different working directory** (as a new Trina chat is), the fork's first request read 20,077 tokens from
  the cache and wrote 14,758 (the part after the working-directory announcement). So a fork's first turn costs about one
  cache write of the conversation, once; the same chat-to-chat fork from the same directory read it all from cache.
- 2.1.305 also has the hidden `--resume-session-at <message uuid>` (the SDK's `resumeSessionAt`). Not used in v1.
- Our launcher takes `sessionRestore.name` and `sessionCollect.name` separately (native/cmd/mycel-launcher/main.go), so
  restoring `<A>.jsonl` and collecting `<B>.jsonl` would need no launcher change. v1 does not need it: the stash copy
  in the fork's own folder is resumed with plain `--resume A` (see "What a fork copies" 5).
- Codex (pinned 0.163.0) has `codex exec fork`, but our Codex turns run `exec --ephemeral` and start fresh every turn
  with the branch history (engine/codex.ts); the API engine too. For them a fork is the copied history plus my own step
  records, which is what their next turn in the original would have had anyway.

## The fork is a chat "others wrote in"

A private chat holding other people's messages is the state the code already knows as `othersWrote` /
`severalAuthors` (a chat that stopped being shared after others wrote in it). The fork **is** that state, on purpose:
remember protection, `others_words`, the withheld rule for the creator and the step-record rules all key on it. What
this means is spelled out below (independent review, 2026-11-26, required changes 1-8).

## What a fork copies

1. **Visible history, up to the end of the branch I am on** (only finished messages; a running answer is not copied).
   Every message as I see it now (`rt.history(... { runner: me, withheld, everyone: true })` and the same
   AnswerSight the app uses): others' questions and answers keep their author. An answer hidden from me becomes one
   row with `withheld_copy = 1` (no content, steps or files): the fork has `shared_at` NULL, so `afterCutover` would
   otherwise judge every copied answer as late and could show a hidden one as an empty bubble. New message ids, the same
   parent chain; `created_at` kept. Copied words do **not** follow later edits or deletions in the original.
2. **A minimal `turns` row per copied answer** (new id; `user_id` = the original runner, `message_id` = the copy,
   `shared_checked` as in the source, **no** `engine_session_blob`). Without it `chatNodes`/`branchNodes`
   (shared-answers.ts ~161, ~239) see no runner and hide my own unrecorded answers from me, `withStepRecords`
   (step-record.ts ~275) drops every turnless row in a several-authors chat, and `stashWrittenBy`, `sharedLater` and
   `viewSteps` misjudge them.
3. **Answer records:** `shared_answer_reads` of each copied answer with ids mapped in both `reads` and `left_out`.
   Read scope (`addSources` of the source scope) and the marks `session_tainted`, `others_words`, `room_outside` are
   copied as they are, never cleared, so remember protection, room cards and the "N answers used places <name> can't
   open" warning on a later Share of the fork work as in the original.
4. **Steps and step notes, as the shared chat gives them to me now.** My own answers: steps and notes as they are.
   Another person's answers: today, in the shared chat, my fresh sessions get their file-tool steps
   (docs/decisions/20261123-shared-chat-others-steps.md; `OTHERS_NOTE_TOOLS`, `notePathsListable` for me, connections
   and browser by name only), but `withStepRecords` keeps them only while the chat is shared (`o.shared`). The fork
   copies **those notes already filtered for me at fork time** into the copied rows' `step_notes` (marked as theirs, so
   the "another person's step" wording stays), so "change the quote Alice made" still knows the path in the fork.
   Nothing beyond what my own fresh session in the original would get today.
5. **Engine context (Claude Code).** If I have my own session on this branch (`ownSessionOn`): **after** the DB commit
   the server copies that stash into the fork's folder as `sessions/<fork>/<A>.jsonl` and then sets the fork's
   `engine_session_id = A`, `engine_session_leaf_id` = the copy of my session's leaf, and `fork_pending = 1`. A failure
   leaves a fork without a session, never a stray file. Because the pointer is the normal one, `SESSION_CHATS_OF` /
   `resetEngineSessions` (access shrink) and `newSession` already cover it: no new cleanup code. The first fork turn
   (`fork_pending`) resumes A with plain `--resume A`: the copy is already isolated in the fork's own folder, so no new
   engine flag and no lockdown re-run. (`--fork-session --session-id <B>` is verified on 2.1.305 and stays an option if
   distinct ids are wanted in logs.) That first turn also gets, like a shared resume:
   - the since-block: the copied messages after my session's leaf, as I see them (with the step notes of item 4);
   - the checks, but for **me only**: the leak check (hidden answers vs the leaf's `left`), `sessionHeld` not null,
     `missingReaders(all, [me])`, `branchLostAttachment`. Not the original's audience check
     (`missingReaders(rest, sharedAudience())`, turn.ts ~1075): someone who joined the original must not drop my fork's
     session. Any failure: a fresh session.
   - one line telling the AI this is now a chat only this person sees, copied from the shared chat, and which tools are
     now there (see "Tools in a fork"); the resumed session keeps the shared chat's recorded system prompt, so this line
     and the rebuilt tool set (`refreshTools` path) carry the change;
   - the person's full current skill list, recorded for this session (`recordListed`): `chat_skill_lists` is one row
     per chat keyed by session, and without it `listedFor` says "stale" every turn and never lists personal skills.
   Then `fork_pending` is cleared and the fork resumes like any chat.
6. **Engine context (no own session, Codex, API engine, too large, a failed check):** the first turn starts fresh from
   the copied history, with the summary when it does not fit (history-summary.ts) and the step notes of item 4. Codex
   runs `exec --ephemeral` every turn (engine/codex.ts), so for Codex this is the same as its next turn in the original.
7. **Attachments: what I see, by reference to the source chat.** Copied rows store `attachmentsOf(srcRow, me)` (the
   resolved view, not the raw JSON: no `from` paths into the source creator's folder, no tiles of others' computer
   uploads the shared view leaves out for me, TC-2022). A chat-file attachment gets `fromChat: <source chat id>`; the
   file route, the AI's `chat:files/` resolver, `attachmentsOf`, export and `branchLostAttachment` resolve it against
   the source chat with `seesChatFiles(me, source)`. Team files stay path references with the normal check. Nobody's
   file is duplicated; files the AI makes in the fork are the fork's own.
8. **Engine, model and effort:** the chat's engine and `model` are copied. Effort is not stored per chat on dev; if
   `feat/model-effort-choice` lands with a per-chat effort, copy it too. A model the person may not use falls back as a
   new chat would.

Not copied: pins, mute, threads under answers, schedules, the original's people or share, open cards (an unanswered
card stays in the original).

**When I later lose the original** (removed from the project, chat deleted): the copied words stay (they are what I
saw); source-chat and team files follow their own access (cards go unavailable; `branchLostAttachment` and the
access-shrink reset drop the fork's session, so its next answer starts fresh from the words). Same rule as a team file
attached in any chat today.

## Tools in a fork

As an "others wrote" chat, the fork today would keep several tools off: `looking_at` ("a chat other people wrote in",
looking-at.ts:50), folder access (folder-access-tool.ts:132), project members (project-members.ts:320) and
`delete_files` (delete-files.ts:115) unless Always allow is on, and the explicit-place / attach asks (`othersWordsIn`);
the chat folder is also emptied every turn (turn.ts ~1510). The browser on my computer is the main thing the AI sends
people to this item for (prompt.ts ~221), so the fork must not keep it off. See decision 3. Memories, personal
connections and schedules work in the fork as in any chat of mine; the `others_words` and taint marks keep guarding
remember and outside addresses as today.

## Where it lives, name, link back, phone

- **Place:** where "Continue in a chat only you see" opens today: the original's project, as a chat only I see (🔒);
  a chat shared with people (no project) → a chat of mine outside projects. The route uses the existing private-chat
  creation check for that place.
- **Guests:** nothing hides the item from guests today (ChatTitleMenu.tsx:57 checks only `chat.shared && !safeOps`).
  Add a web gate: shown only where the guest may start a chat (their one project, `guestPlace` / `heldProject`) and has
  AI (`guestAi !== 'none'`); the route returns 403 otherwise and the web falls back to today's box.
- **Name:** the original's title, unchanged (title_source copied). The 🔒 and the line below tell the two apart.
- **Link back:** one line above the copied messages: "‹title›에서 이어 왔어요 / Continued from ‹title›", a link while I
  may open the original, plain text when I may not or it is gone. The original shows nothing; others never learn a
  private chat exists (sharing model).
- **Box:** opens empty and focused (today it holds my last question because nothing carried over).
- **Phone:** the same title menu item and the same line; the app is the web UI.
- **UI count:** no new button or menu item; the label stays (the AI quotes it, prompt.ts `privatelyMenu`). Added: one
  line in the fork. Removed: the prefilled question.
- **AI wording:** prompt.ts ~220-221 says the item "starts one … with the question already in the box"; it changes to
  "opens a chat only you see with this conversation so far", so the AI never asks the person to retype.

## Cost and caching

A fork that resumes my own session sends the whole conversation once more: the measured first fork turn from another
working directory read 20,077 tokens from cache and wrote 14,758; later turns cache as usual. A fresh-start fork costs
what any fresh session costs. Today's empty chat is cheaper only because the person then re-explains and the AI redoes
the work.

## Decisions (owner, at most 3)

1. **Entry points.** A: only the existing title-menu item in shared chats, fork at the end of my branch, like Claude
   Code's `/branch`. B: A plus "여기서부터 새 채팅으로" in each answer's menu (ChatGPT's "Branch in new chat"), shared
   chats only. C: B in private chats too. **Recommend A** (reviewer agrees). No new button; private chats already have
   edit/regenerate branches; B/C need a fresh session per answer or the hidden `--resume-session-at`, and can come from use.
2. **Other people's words in my private copy.** A: copy everything I can see now, names kept; hidden answers stay one
   line; others' step notes only as the shared chat gives them to me now; later edits in the original not followed.
   B: only my own questions and answers plus a summary of the rest. C: ask the others. **Recommend A** (reviewer
   agrees). They are words I already see and could copy by hand; ChatGPT and Claude Code copy what the viewer saw.
3. **Personal tools in a fork that holds others' copied words.** A: keep today's "others wrote" rules (browser view,
   folder access, members, trash stay off or ask) and say so in the fork line. B: when the only other people's content
   is the copied history, these tools ask with the normal card and the person's Always allow ends the asking, as in
   their own chat; the `others_words` and taint marks keep guarding remember and outside addresses. **Recommend B**
   (the reviewer's pick too): the item exists to reach personal tools, Claude Code has no such limit, and Rule A says
   the person's own Always allow is final.

## Risks

- Privacy: the fork must never copy what I cannot see now (withheld answers, others' notes beyond today's rule, others'
  sessions, other people's computer uploads). The copy reads through the functions the app and the engine use for me.
- Local-login mode (office Mac, dev): the session copy restores into the fork's own project folder of
  `~/.claude/projects`; Claude Code looks there first, so the original's file is never picked.
- Stash size: up to 40 MiB copied per fork; counted against storage like a session.
- Five languages, phone and desktop; the AI's quoted label stays the same.
