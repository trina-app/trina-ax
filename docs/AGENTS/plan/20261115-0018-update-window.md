# While Trina updates: a waiting page, messages that wait, a Share dialog that says why

- Date (UTC): 2026-11-15 00:18
- Branch: `fix/qa-1115-update-window`
- Status: done
- Where: server/src/system (the update's stand-in), shared/src/api/client.ts, web/src (Team AX core), mobile/. Why:
  chat, sharing and the phone app's failure screen are core (docs/REPOSITORY-RULES.md)
- Version impact: patch, a fix of what people see during an update (the phone part reaches phones with the next store
  build)

## Goal

QA TC-2260. While an update migrates the database the server answers 503 from a stand-in
(`server/src/system/migrate-start.ts`). Today:

1. a shared chat link opened in a browser shows the stand-in's raw JSON;
2. a message sent meanwhile ends "Not sent … Send again" and is not sent when the server is back;
3. saving the Share dialog says "Couldn't save".

People should see "Trina is updating", in plain words, and things should go on by themselves when it is back.

## Scope

In:
- Stand-in: a browser page load (GET, not `/api/`, accepts HTML) gets a small HTML page in the page's language
  ("Trina is updating" · back in a few minutes · opens by itself) that reloads itself; API answers keep the JSON and
  carry `params.reason: "updating"` and an `x-mycel-updating: 1` header. No time estimate: the server knows how far the
  copy is, not how long the migrations after it take, so the page says "in a few minutes".
- `shared/src/api/client.ts`: the header (and the relay's `team_maintenance` page, the same situation on hosted teams)
  becomes `params.reason: "updating"`, as `team_waking` does.
- `web/src/lib/serverUpdating.ts`: one place that knows Trina is updating (an answer with that marker), asks
  `/api/health` until it answers OK, and resolves `whenServerBack()`. `isServerUpdating(e)` in `lib/api.ts`; it counts
  as a connection error (it passes by itself).
- Uses: the chat outbox (`store/chats.ts deliver`) and room sends (`store/rooms.ts post`) keep the message with an
  "updating" note and send it once when the server is back, with the same `clientMessageId` (the server's idempotency);
  the message box's "not sent" line (a new chat) says updating and sends once when back; the Share dialog says
  updating, keeps the picks and saves again when back; a list that could not be read says updating (LoadError).
- Phone app: its own failure screen says "Trina is updating" when `/api/health` answers "migrating" (it already
  retries by itself). Desktop shows the server's page as it is (an HTTP 503 page is not a failed load there).

Out: an estimate of the remaining minutes; an app-wide banner.

## Steps

1. Stand-in page + marker, unit test (tests/unit/p1-migrate-start.test.ts).
2. client.ts + lib/serverUpdating.ts + api.ts helpers, unit tests.
3. Chat outbox, room sends, Composer, Share dialog, LoadError; strings en → ko, id, ja, es, zh.
4. Phone app health kind + strings, unit test.
5. e2e: a 503-updating server via page.route; changelog fragment; typecheck, i18n, unit tests.

## Risks

A message must never go twice: the retry reuses the same `clientMessageId` and the stand-in stores nothing. The
updating wait has no time limit while the page is open (the update ends or the person deletes the message). No
migrations.
