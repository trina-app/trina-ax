## Goal

A promo video made in a chat on a Linux team server (potenlab.trina.app, every hosted team, a self-hosted
`install-linux.sh` server, a Docker server built with the video group) gets [영상 파일로 받기] for the person who
asked and for everyone who may open that chat (a shared chat, a project chat), and the AI's `save_promo_video` /
share-to-room path sends the MP4. Where the MP4 truly cannot be made, the panel says so in one line, never a silent
missing button.

## Scope

In:
1. **The list**: a new group `video` (install `default`, not `--minimal`), artifacts `node` (the list's pinned Node 22,
   already there for srt) and a new artifact `hyperframes` (the npm tarball 0.9.15, sha256 and size, like `srt`;
   installed with `npm ci --ignore-scripts --omit=dev` from the existing lock `scripts/promo-video/hyperframes/
   package-lock.json`, which pins every package by integrity). It uses the `browser` group's chrome-headless-shell and
   the `media` group's ffmpeg (both on every default install already). Nothing in one install script.
2. **packages.sh**: `pk_node_install` (the list's node in `/opt/trina/node-v<v>`, link `/opt/trina/node`, the same
   layout install-srt.sh uses, which then finds it) and `pk_video_prepare` / `pk_video_install` (the CLI tree in
   `/opt/trina/hyperframes/<version>-<lock sha12>`, checked by `node cli --version`, `current` switched only to a tree that
   answers; the one before kept until the next switch), called by `sync` (mycel-ctl update: every existing Linux
   server, hosted ones included), by install-linux.sh (prepared before the server stops, switched after: the image's
   customize.sh runs it, so the hosted image has it) and by the Docker image when `TRINA_AX_PACKAGE_GROUPS` names
   `video`. The bundle ships the lock as root files (`root/hyperframes/`), so a changed lock is a root change.
3. **The server** (`promo-video/render.ts`): `mp4Available` on Linux = the pinned node, the CLI in
   `/opt/trina/hyperframes/current` (or `MYCEL_HYPERFRAMES_DIR`), a trusted headless browser (`findPdfBrowser`), ffmpeg,
   and bwrap isolation; any mode (hosted and production too). macOS stays as it is (a development Mac only). On Linux
   the CLI runs in the converters' isolation (`isolatedCommand`: bwrap, no network, read-only system, only the work
   folder writable) with HOME/TMPDIR in the work folder, `--workers` by the machine (1 on small machines), in a print
   cgroup leaf when there is one, the same one-at-a-time queue, time limit (longer on Linux) and shutdown kill.
   `PromoVideoInfo.mp4` gets `why` (`not_installed` | `unsupported`) when it is not available.
4. **The panel**: when the server says not available, a short muted line in the header instead of the button
   ("이 서버에서는 영상 파일을 만들 수 없어요" / on Linux before the install: "영상 파일 기능을 준비하는 중이에요. 서버 업데이트
   뒤 받을 수 있어요"), with the five languages. Same for everyone who may open the chat.
5. Docs: a decision file `docs/decisions/20261123-linux-video-mp4.md` (supersedes the "Linux team server: not in this
   round" paragraph of V and the "Where" line of 20261116-save-promo-video.md), `changes/linux-video-mp4.md`.

Out: the srt queued-job design of V's handoff (not needed: the converters' bwrap isolation runs it); the office Mac
(macOS production stays off, unchanged); Docker images without `video` in the build argument (they get the notice).

## Risks

- Disk: +~110 MB (CLI tree) and +~30 MB (node, shared with srt) per Linux server and in the hosted image.
- Memory/CPU: one render ~1 GB peak with one worker (measured in Docker, Debian 13 arm64), ~80 s on 4 cores; one at a
  time per server; the print leaf / time limit bound it.
- Security: the page is ours (slots checked, no script, pictures copied with the chat owner's permissions); the
  browser runs with `--no-sandbox` (HyperFrames) inside bwrap with no network, read-only system, as the server account.
- No migration.
