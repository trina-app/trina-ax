## Goal

Without the dev environment (Office Mac, teams from before 2026-11-06, Ubuntu/Debian 12 servers) the AI refused
everyday data work on a 50k-row CSV or xlsx: pivots, totals, top-N, splitting a CSV, monthly charts ("the heavier
data-processing option isn't available"), 7 of 42 audit tasks. Claude Code does these with one `python` or `awk`
call. Give the AI one built-in tool that works on every install.

## Scope

In: `query_data { paths, sql?, sheet?, header_row?, show_rows?, save_as?, split_by? }`.
- Loads CSV, TSV, xlsx/xls/ods (one table per sheet) and JSON/JSONL files the person may read into a SQLite database
  in an empty work folder, inside the office worker (bun:sqlite, already in the stack), run through the converter
  isolation (tools/isolate.ts): no network, reads only its work folder, a time, memory, output and disk cap.
- Without `sql`: the tables, their columns and types, row counts and a few sample rows. With `sql`: one read-only
  SELECT / WITH; small results inline, bigger ones cut with a count and a hint.
- `save_as` (.csv / .tsv / .xlsx): the whole result saved through make_file's save path (placeProduced: permissions,
  versions, conflict copies, file events) after the wider-audience check (confirmSources). `split_by`: one file per
  value of a result column ("split by region into 3 files").
- Read record: every input joins the turn's read scope, read hashes and sources, as a read does; the shared-chat read
  card sees `paths` (PATH_ARGS) and `save_as` (WRITE_TARGET_ARGS).
- Prompt: a rule that says to use it instead of refusing or counting with grep; the app map's dev-environment words no
  longer say big data files need it.
Out: charts as pictures (finding N4), formulas or styling in the saved xlsx (make_file does that from a CSV), Google
Sheets, files shared by link (/f/...).

## Engine

bun:sqlite in the office worker: no new binary, no new package, the same isolation and bundle as the spreadsheet reader.
DuckDB (MIT, so licence-compatible) would mean a 30-60 MB native library per platform (Mac arm64/x64, Linux
x64/arm64, Windows), listed in scripts/system/packages.json with sha256s, a root update, and a native module loaded in
the worker: not worth it for office-sized data, where SQLite on disk handles 6M rows in seconds.

## Steps

1. `server/src/files/data-query.ts`: the worker side (parse, type columns, load, query, write results).
2. `server/src/tools/query-data.ts`: the tool (authorize, copy inputs into the work folder, slot, isolated run, place).
3. Shared contract, tool lists, prompt rule, step label (6 languages), app map words, changes and decision files.
4. Unit tests (parsing, typing, SQL guard, end to end through the isolated worker, saving, split, refusals), tool-list
   tests, typecheck, Bun 1.3.12; real-AI check on a QA team copy with the dev environment off.

## Risks

Hostile files: parsed only in the isolated worker, like the spreadsheet reader. SQL: one statement, SELECT/WITH/VALUES
only, `PRAGMA query_only`, no extensions; the database holds only the copies of the files passed in. Big inputs: the
memory watchdog (2 GB), 180 s, a disk cap on the work folder, two queries at a time on the server.

## Tests

`tests/unit/c-query-data.test.ts`, the tool-list tests, `bun run typecheck`, `bun run check:prepush`.
