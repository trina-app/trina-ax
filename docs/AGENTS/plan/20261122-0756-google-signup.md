- Date (UTC): 2026-11-22 07:56
- Branch: `feat/google-signup` (stacked on `feat/google-login`, which is not merged yet)
- Status: built, not merged yet
- Where: trina-ax `server/src/auth/` (accounts.ts setup and acceptInvite, team-links.ts joinTeamLink, google-login.ts
  new intents, a new reauth module), `server/src/http/route.ts` (owner-reauth / admin-reauth), the admin handover
  rules, `web/src/pages/Auth.tsx` (setup, invite, join pages), Settings › Security & devices, `shared/src/api/`.
  No control plane change: the hosted sign-in broker (part B of
  [the Google login plan](20261122-0454-google-login.md)) already answers who signed in. Why: sign-up with Google
  needs a Google client the server can use: a hosted team has one through the hosting service (broker), a
  self-installed server only with its own client file; a fresh self-installed server shows only the password form.
- Version impact: minor. New endpoints and flows; the migrations are not released yet (131 is edited in place).

## Goal

Trina AX has not launched. A customer signs up and pays at account.trina.app with Google, then the team server asks
for a username and a password, and every invited employee has to make a password too. The founder (2026-11-22):
plan sign-up with Google now and build it, before launch, so nobody has to be moved later.

## Scope

In:
1. **First owner with Google.** The setup page (`/setup#token=…`) offers **Start with Google** beside the password form.
   The setup token is checked exactly as `setup()` checks it today (local / relay rules, tokenGuard). The team name,
   language and time zone the owner typed travel sealed in the flow; Google's return creates the team and the owner
   in the same transaction as `bootstrapOwner` (only while no user exists), with the Google identity and no password.
   Username: suggested from the Google address's local part (cleaned to the Username rule, made unique), name from
   Google; both editable later in Settings.
2. **Invited people and team links with Google.** The invite page (`/invite/<token>`) and the team link page (`/join`)
   offer **Join with Google**. The flow keeps the invite or link id (never the raw token) and the username / name /
   language the person chose, sealed. Google's return runs the same checks as `acceptInvite` / `joinTeamLink` in
   the same write (single use, seats, the maker re-check, link uses): both use one "create the account" step that
   takes a password hash OR a Google identity. What follows a join (recordJoin, afterLeadJoin, notifyTeamJoined,
   memberJoined, …) runs after the commit, as today. A Google account already connected in this team signs that
   person in instead: read inside that write before anything is used, with the Google sign-in's refusals (turned off,
   a temporary password), the invite or link left unused and no role or groups applied (an admin invite opened by a
   member does not make them an admin); two tabs with one Google account meet there. A username taken meanwhile comes
   back as `username_taken`; the page keeps the token in the tab to try again. Guest invites stay password-only (out).
3. **A password is optional.** `users.password_hash` NULL for accounts made with Google. Password sign-in for such an
   account answers like a wrong password. Settings › Security & devices: **Set a password** for an account without
   one (needs a fresh Google check), Change password as today otherwise. Disconnect Google only while a password
   exists (unchanged rule).
4. **Re-check without a password** (built by the reauth branch; its decision file is the reference: a Google re-check
   only for accounts without a password, no `max_age` / `auth_time`, no re-check token, the apps re-check in a
   browser; the text below is the first draft). One `verifyReauth()` replaces every place that checks a re-entered password today:
   `owner-reauth` / `admin-reauth` in `server/src/http/route.ts`, and the direct checks (find them all with
   `grep -rn verifyPassword server/src`: admin delete member, own account deletion request, voice key, office update,
   current password, Google connect). It takes `password` (as today) or `reauthToken`: single use, 5 minutes, bound to
   the session, minted by a fresh Google round trip (intent `reauth`: the same session, the same Google `sub` as the
   person's connected identity, `prompt=select_account` and `max_age=0`, `auth_time` checked when Google sends it).
   Wrong tries count on the person's re-check limit as today (`reauthKey`, `onReauthLocked`). Web: ReauthDialog shows
   **Confirm with Google** for a person without a password; Google opens in a new window, the dialog waits for the
   token (polling the flow), then sends the original request.
5. **Owner handover and admins** (the reauth branch's decision file). A person who signs in with Google may become owner or admin. The W6 line "There is no
   sign-in without a password to bypass it" (`docs/DECISIONS.md` "W6 — Onboarding v6: easy owner handover") is
   superseded: a Google identity is a credential like a password. The temporary-password rule stays.
6. **Recovery stays as it is.** An admin's temporary password or a reset link gives a person without a password one
   (and disconnects Google, as decided in part A1); the hosted owner recovers through the console, which signs in with
   Google too.
7. Docs, changes, decisions, six languages, the repo guards (features, security cases, scenarios, docs:api).

Out:
- Guests with Google. Joining without an invite because of a `@company.com` address. "Google only" teams.
- Sign-up with Google inside the desktop and phone apps' own windows: the setup, invite and join pages offer Google in
  a browser; an invite opened in the phone app keeps the password form for now (say so in Risks).

## Risks

- A Google re-check on an open laptop can be one click (Google may not ask for its password again even with
  `max_age=0`). It still stops a session cookie used on another machine, and the token is bound to the session.
- An account without a password whose Google account is suspended or lost: an admin gives a temporary password; the
  owner recovers through the console (hosted) or the server's CLI reset link (self-installed).
- The phone app opens invite links itself (universal links): there the person joins with a password until the apps get
  their own sign-up flow.
- Migration 131 changes in place: safe only because it is not on dev yet; check before merging.
- Older desktop and phone builds show only the password form on the join pages; people without a password need the
  store builds with Google sign-in before launch.
- A browser signs up with Google only at the address Google (or the hosting service) returns to: office, Tailscale and
  LAN addresses have none, so people there join with a password.
- Starts: a sign-up start does not count on the per-address Google start limit (an office joining from one address);
  an invite's or link's own limit and the open-flow cap bound them.
