## Findings (local Docker run, same image and suite as CI)

- S12 (product): in a chat shared with people a read-only folder that holds a folder not everyone may open (shared/
  with shared/hr-limited) is given entry by entry (srt/mounts.ts, QA TC-4929). Its top is then srt's empty in-sandbox
  place, which is writable: `echo x > shared/new2.md` and `mkdir shared/dir2` exited 0 and the file was never kept.
  A command reported success for a write to a read-only folder.
- S9b, S9c (test): the runner refuses a shared chat's cwd in a folder the chat does not show (runner.ts
  sharedCwdShown); the suite's own copy of the runner did not, so bwrap fell back to the run's HOME. Nothing of the
  hidden folder showed.
- S14 (TC-4929), S16 (logs), S16d (test): nothing was listed or read; the checks matched the path the attack typed
  itself, echoed back in `cat:`/`ls:` "No such file or directory" lines.

## Steps

1. mounts.ts: `readOnlyTops(v, given)` (read-only folders opened entry by entry, none under a writable entry);
   `writePins` writes their list as a third file and `entryGuard` makes those places read-only (`chmod a-w`) inside
   the sandbox before the command. runner.ts passes them (Linux).
2. srt-attack.ts: the harness refuses a cwd as the runner does (sharedPathAccess) and passes the read-only tops; S14,
   S16 and S16d look at listings and contents, not at error lines that repeat the attack's own path.
3. Unit test in tests/unit/shared-hidden-subfolders.test.ts.
