## Goal

QA TC-4972..TC-4978. Seven size caps were set when each tool was first written and never measured again. The AI should
work like Claude Code: a cap stays only where memory, disk or another person's data needs it, and then the AI is told
what was cut and how to go on.

## Scope

In:
1. PDF tools (edit, merge, split, stamp): 40 MB per call -> a value measured against the office worker's 2 GB memory
   cap; the worker's answer cap for these tools raised to match; the worker's time grows with the input.
2. resize_images: 32 MB per photo (TS and the Go helper's ResizeInputMax), 200 MB per call, 60 s -> 150 MB, a larger
   per-call total, 120 s; memory measured on the helper.
3. save_room_file: room files over 50 MB refused -> a streamed copy up to the room's own limit (1 GB), hashed on the
   way, held files refused by that hash, disk checked before the copy. Every permission and audience check unchanged.
4. read with `versions`: the changes cut at 8,000 characters with no read-on -> 40,000 characters per read and `offset`
   (a line of the changes) to read on; the cut says where.
5. Team files attached to a mail: 10 MB / 10 files -> 18 MB (Gmail's 25 MB after base64 and line breaks) / 20 files.
6. Artifacts: 2 MB -> 10 MB, with the disk check before a version is stored.
7. make_file charts: 10 -> 50 per workbook (the HYPERLINK/INDIRECT rule is not touched).

Out: the person's own "Save to team folder" button for room files (rooms/save-to-team.ts, also 50 MB): a route with its
own web text, left for a follow-up.

## Steps

1. Measure pdf-lib in the office worker and the Go resize helper on large inputs.
2. Change the constants, the texts that state them, and the room copy.
3. Unit tests that fail on the old values; typecheck; check:prepush on Bun 1.3.12.
