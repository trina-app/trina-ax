## Goal

A team brings an outside person (a client, a freelancer) into ONE room or ONE project without that person seeing the
rest of the team. Phase 1 builds what keeps everything else closed plus the server side of the invite. Screens come in
phase 2.

Owner decisions (2026-11-14, final):
- A guest is in exactly one place: one group chat or one project. Never several. Putting them into a second place is
  refused (409 `conflict`, params.reason `guest_one_place`, message "A guest can be in one room or project only. To add
  them to more, make them a team member." / ko "게스트는 방이나 프로젝트 한 곳에만 들어갈 수 있어요. 여러 곳에 넣으려면
  팀원으로 초대해 주세요."). The way out is "convert to member". No admin "move place" endpoint.
- Removed from their one place: the account is disabled.
- Everything else is denied by default; only an allow-list is open.
- Guest AI is off by default: `none | team | own`. `team` = a team connection assigned to the guest personally plus a
  usage limit (existing per-person assignment and budgets). `own` = their own Claude/Codex sign-in. The hosted trial
  credit never pays for guests; on a self-hosted install a guest never runs on the host's own sign-in.
- Caps: Free 3, Starter 10, Team 30, Business 100 (PlanFile.maxGuests, written by the control plane later).
  Self-hosted: no cap. Guests take no seats.
- One guest type, no expiry, a member is never changed into a guest, guests join no groups, DMs never count as a place
  (a guest may DM only people of their place), other members' project chats are not visible to a guest.

## 1. Schema: `server/migrations/122_a_guests.sql` (A range, `-- min_compatible_reader: 8`)

```sql
ALTER TABLE users ADD COLUMN guest INTEGER NOT NULL DEFAULT 0 CHECK (guest IN (0, 1));
CREATE TABLE guests (
  user_id TEXT PRIMARY KEY REFERENCES users(id) ON DELETE CASCADE,
  place_kind TEXT NOT NULL CHECK (place_kind IN ('room', 'project')),
  place_id TEXT NOT NULL,              -- rooms.id (kind 'group') or projects.id
  ai TEXT NOT NULL DEFAULT 'none' CHECK (ai IN ('none', 'team', 'own')),
  team_credential_id TEXT REFERENCES engine_credentials(id) ON DELETE SET NULL,  -- ai 'team' only
  invited_by TEXT REFERENCES users(id) ON DELETE SET NULL,
  created_at TEXT NOT NULL
);
ALTER TABLE invites ADD COLUMN guest_place_kind TEXT CHECK (guest_place_kind IS NULL OR guest_place_kind IN ('room', 'project'));
ALTER TABLE invites ADD COLUMN guest_place_id TEXT;
ALTER TABLE invites ADD COLUMN guest_ai TEXT;  -- JSON GuestAiChoice, null on member invites
```

- Why not `role = 'guest'`: `users.role` has `CHECK (role IN ('owner','admin','member'))`. Widening it needs a rebuild
  of `users` (104 foreign keys, `foreign_keys = ON` inside the migration transaction: a DROP would cascade), and
  `writable_schema` is blocked (defensive mode, tested). The repository never rebuilds tables (WORKPLAN §4). So a guest
  is stored as role `member` + `users.guest = 1` and READ as role `guest` everywhere (below).
- `SCHEMA_READER_LEVEL` 7 -> 8 (server/src/db.ts): an older build would read a guest as a full member.
- `users.invites.role` has no CHECK: a guest invite stores `role = 'guest'`.

## 6. Invites

- Shapes: `CreateInviteBody { role:'guest', guestPlace, guestAi }` (admin endpoint) and `POST /api/guest-invites
  { place, ai, expiresInHours }` (user endpoint). Stored in `invites.role='guest'`, `guest_place_kind/id`, `guest_ai`.
- Who: owner/admin any place; a member: a group chat (`rooms.kind = 'group'`, not archived) they are in; a project only
  if they are its creator (`projects.created_by`) and still read its folder. `team` AI: only owner/admin (they manage
  connections and budgets), the credential must be a team connection (no `owner_user_id`). Guests cannot invite.
- `assertGuestFree` at create (409 plan_limit reason guest_limit) and again at accept, inside the write transaction.
- `inviteInfo` (public): role 'guest' and the place name only (no member names).
- Accept (auth/accounts.ts `acceptInvite`): inside the transaction re-check the inviter is still active and still
  allowed for that place (same rules as create), the place still exists, the cap; insert the user with role 'member'
  + `guest = 1`, the `guests` row, no groups; join: a group chat -> room_members add (Rooms.invite path, events); a
  project -> a person rule `write` on its folder (writeFolderAccess, afterAccessChange after the commit); `team` AI ->
  `guests.team_credential_id` + `budgets (user, month, limitUsd, block)`, never an engine_credential_assignments row.
- One place: every path that puts a person into a group chat or a project calls `assertGuestMayJoin`:
  rooms/service.ts `createGroup`, `invite`; chat/project-access.ts `saveParticipants` (members panel and the AI's
  change_project_members); admin folder rules (admin/folders.ts write of a person rule on projects/<name> for a guest);
  invite accept for an existing session (refused: an account never accepts a second invite).
- Removal -> disabled: rooms/service.ts `remove`/`leave` of a group chat, chat/project-access.ts save that drops the
  guest, project-leave, project delete/trash, group chat archive: after the write, if the guest is no longer in their
  place (`inPlace`), set `status = 'disabled'` and end their sessions (`disableGuestIfPlaceless(ctx, id)`, also run by
  a check at start and after access changes).
- Convert: `POST /api/admin/users/:id/convert-guest`: admin; target must be a guest; `assertSeatFree` inside the
  transaction; `guest = 0`, delete the `guests` row; they keep their place (room membership and project rule); audit
  `user.convert_guest`; realtime `disconnectUser` so sessions reload the new role.

    second place refused through invite-accept (existing guest), add-member on a room, and project participants.
18. Removal from the one place (room remove, room leave, project participants) disables the account.
19. Role reads: `GET /api/me` and admin user list say role 'guest'; admin PATCH cannot make a member a guest or change
    a guest's role/groups.
20. Migration: reader level 8, a fresh DB has the columns; Go plan reader test for maxGuests.
Plus: full `bun run test:unit`, `bun run typecheck`, `bun run check:docs` (`docs:api` regenerated), `check:i18n`.

## 8. Risks

- The role column is not widened: any raw SQL that reads `role` without `roleSql` sees a guest as a member. Mitigation:
  all role reads in server/src use roleSql (audit list in §4.1) and a test greps server/src for `role` selected from
  `users` without it.
- Presence and realtime events: per-socket filtering of team-wide broadcasts (presence, people/profile change events,
  rooms events) may miss an event type; the plan filters presence and profile events; other team-wide events carry no
  names (checked in the review pass).
- Project membership for "place people" uses the folder rules (who reads projects/<name>), which include the owner and
  admins only when they are members (zone rules), so a guest may DM the project's members only.
- A guest's own chats in their project follow the team default (visible to project members). Least change; flag for
  the owner.
- `maxGuests` absent from a hosted plan file: the server allows 3 until the control plane writes it (narrowest).
- Phase 1 has no UI: a guest who signs in to the web app sees screens that 403. Expected until phase 2.

## Result

Built as planned with the one-place rule. Tests: tests/unit/a-guests-*.test.ts and b-guests-turn.test.ts (one per leak
path, real guests through invite + accept), the permission matrix cases, the role-read list. An independent security
review found no must-fix; its should-fix items (DMs closed once the pair no longer shares a place, prompt-carried team
rules in the share check) and notes (no web search or sub-agents for guests, no guest writes in a project's skills/,
group chat size at accept, the placeless check at start) were fixed. After the rebase on dev, guests are also kept out
of chats shared with people and groups. Phase 2 reads Me.guest, User.guest, Person.guest, InviteInfo.guestPlace and
PATCH /api/admin/users/:id/guest-ai. The control plane (private repo) sets PlanFile.maxGuests later.
