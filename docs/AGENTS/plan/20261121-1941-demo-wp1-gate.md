# Free-roam demo gate pages: what Trina AX is, language memory, a clean start, honest waits

- Version impact: patch, user-visible fixes on the demo's gate pages, no API or data change

## Goal

The free-roam demo QA of 2026-11-22 (four testers, en/ko/ja/zh/es/id) found five problems on the gate's own pages:

- F7: the landing page never says what Trina AX is.
- F10: the landing and "session ended" pages ignore the language the visitor used in the app (only `?lang=` or the
  browser language count).
- F11: a draft attachment (and draft text, and the send queue) from one visitor shows up for the next visitor in the
  same browser tab: every demo copy has the same user id, and the web app keys those by user id.
- F18 (gate part): `.note { word-break: keep-all }` makes Japanese and Chinese break only at punctuation; the zh landing
  line reads translated.
- F19: the limit page gives no time, and it is wrong to say "about an hour" for two of its three reasons; the busy and
  error pages have no retry.

## Scope

In:
- `lead` line above the landing heading (all 6 languages; en is the source, ko as specified, es/id formal register).
- The landing `note` says bigger tasks count more.
- `localeOf(query, acceptLanguage, allowed, cookieLocale)`: `?lang=` (or the form's `lang`), then the `mycel_locale`
  cookie, then Accept-Language, then en. The cookie passes the same `allowed` check as the query, so nothing else can
  reach `<html lang>`.
- The successful start 303 sets `mycel_locale=<checked locale>; Path=/; Max-Age=31536000; SameSite=Lax; Secure` (not
  HttpOnly: the web app writes the same cookie) and sends `Clear-Site-Data: "storage"`.
  - The value is exactly `"storage"`, never `"*"`, `"cookies"` or `"cache"`: in Chrome `"cookies"` clears the whole
    registrable domain (trina.app). `"storage"` is origin-scoped and leaves cookies alone, so the new session cookies
    set in the same response survive.
  - Only on the successful new start. Never on `/__demo/resume` (the same visitor's own copy: it would wipe their
    draft), never on the "already live" redirect, never on busy, limit, check or error.
- The limit page by reason: `hour` → "about an hour"; `day` and `ip_live` → "tomorrow".
- Busy and error pages get a "Try again" link to `/`.
- `.note` keep-all only for `html[lang="ko"]`; the zh landing line rewritten.

Out (other packages): the web app's bar, chips, counter and strings (WP2), connector cards (WP3), demo content (WP4),
banner and prompt (WP5). If Clear-Site-Data does not clear sessionStorage in a browser, the fallback (`/?fresh=1` and
the web app's sign-out cleanup on a free-roam boot) needs a web change, which goes to WP2.

## Steps

1. pages.ts: words (`lead`, `limitLaterP`, `retry`, new `note`, `limitP`), `localeOf` with the cookie, `limitWait`,
   `renderPage` with the limit reason and the retry link, the ko-only keep-all.
2. public.ts: pass the cookie to `localeOf` (start and the page path), the limit reason to `page`, and on the
   successful start the locale cookie and `Clear-Site-Data: "storage"`.
3. Tests: unit (cookie order, a cookie that is not a locale, lead in every language, retry links, limit texts per
   reason); gate (ended page by cookie, start headers, no Clear-Site-Data on resume or any refusal, limit texts).
4. Manual: Chrome (and Safari if it can be driven here) against a local gate: after a new Start, no `mycel.*` keys in
   localStorage or sessionStorage.

## Decisions

## Risks

- Clear-Site-Data also unregisters the PWA service worker (the app registers it again) and drops the locale saved in
  localStorage (the app falls back to the cookie the gate now sets, or `/api/me`).
- Another open tab of an older demo copy loses its local drafts on a new Start in the same browser.
- Browser support for clearing sessionStorage through a redirect's Clear-Site-Data is checked by hand (step 4). It
  failed in WebKit, so the fallback is in: see Result.

## Tests

`bun run typecheck`, `bun run check:prepush`, `bun run check:i18n`, `bun test demo-gate/test`, every
`tests/unit/*demo*.test.ts`.

## Result

- Done as planned. Manual check (2026-11-22) against a local gate (test harness, real gate process, https on
  localhost): Chrome 157 clears localStorage, sessionStorage and IndexedDB on the new start and keeps `__Host-tdg`,
  `__Host-sid` and `mycel_locale`; "Continue as Mina" (resume) keeps everything. WebKit (Playwright's WebKit build)
  keeps all three storages: Clear-Site-Data on the 303 is not honoured.
- So the successful start now lands on `/?fresh=1` (the review's fallback, M3). The web app part (on `fresh=1` in a
  free-roam boot, run the sign-out cleanup of the tab's storage, then drop the parameter with `history.replaceState`)
  belongs to the web package (WP2). Until it lands, Chrome is fixed and Safari is not.
