# The AI unzips a zip file: unzip_file

- Date (UTC): 2026-11-18 07:00
- Branch: `feat/ai-unzip` (off `dev`)
- Status: in progress
- QA: TC-4847
- Where: Team AX core (`server/src/tools/`, `server/src/files/`). Why: files are core (docs/REPOSITORY-RULES.md)
- Version impact: minor, a new AI tool

## Goal

A person attached a zip in a project chat, had the AI put it in the project folder, then said "zip 풀어서 놔둬". The AI
answered that it cannot unzip or look inside and asked the person to unzip it on their computer and upload again. No
tool extracts an archive. Add one.

## Scope

In: one tool, `unzip_file`, for a .zip the person may read. Default target: a new folder next to the zip named after it
(" (2)" when the name is taken; never over anything). `to_folder` puts the contents elsewhere; `list_only` lists what is
inside without saving. Subfolders and names kept; names decoded as UTF-8 (flag, Info-ZIP Unicode path field or valid
UTF-8) else as CP949 (zips made on Korean Windows). Junk skipped (`__MACOSX/`, `._*`, `.DS_Store`, `Thumbs.db`).
Refused: absolute paths and `..` (nothing saved), zip64, encryption, damaged zips, too many entries or bytes (the
zip-guard limits); symlinks and device files are skipped and named. Every file is saved through make_file's path
(placeProduced: permissions, versions, file events, text index, published change) after the wider-audience check
(confirmSources) for the zip; new folders are recorded as the move tools do. A partial failure says what was and was not
saved.
Out: other archive formats (7z, rar, tar, alz, egg), password-protected zips, nested zips.

## Steps

1. The zip-guard central-directory reader shared with checkZip (no behaviour change to checkZip).
2. `server/src/files/unzip.ts` (plan: names, paths, junk, limits) and `server/src/tools/unzip.ts` (the tool).
3. Shared contract, tool lists, prompt rule, step label (6 languages), changes file.
4. Unit tests (c-unzip), tool-list tests, typecheck, Bun 1.3.12; scripted-AI check on a local dev server.

## Risks

Zip slip, bombs and odd entries: the central directory is checked before anything is written (declared total, ratio,
count), each entry is inflated with a hard output cap and its real size and CRC must match. Paths are built from checked
segments only (badSegment) and every file is placed through authorize. Inflate runs on the zlib thread pool, one entry
at a time.
