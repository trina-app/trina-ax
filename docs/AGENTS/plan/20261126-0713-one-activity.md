# One Activity: every notice in one place, like Slack

- Date (UTC): 2026-11-26 07:13
- Branch: `feat/one-activity`
- Status: done (UX review 2026-11-26: changes, applied below)
- Where: trina-ax `web/` (no server or API change). Why: navigation, the rail, the phone tabs and the Activity list
  are the web app's (see docs/REPOSITORY-RULES.md)
- Version impact: minor. People see a different navigation: the 대화 row goes, and mentions, thread replies and DMs move
  into 활동 with a different count. There is no API change and no migration.

## Goal

The owner (2026-11-26) asked whether having both 활동 and the 대화 row "멘션·스레드" is right, and whether Slack does
this. It does not. Slack has one Activity with filters, so we fold notices into one 활동 the way Slack does.

Today, on a computer:
- The 활동 panel (`panels/ActivityPanel.tsx`) lists only the app's own notices. Its chips are 전체 · 트리나 · 요청, with
  the line "멘션·스레드는 대화에 있어요 ›" on top.
- Mentions, DMs and thread replies are in a second view of the same feed: 대화 › "멘션·스레드" (`/activity?in=chats`,
  `panels/ChatsPanel.tsx`), with the chips 전체 · 멘션 · 스레드.

Today, on a phone:
- 나 › 활동 (`/activity`) already shows everything, with the tabs 전체 · DM · 멘션 · 스레드.
- 대화 still starts with a "멘션·스레드" row that opens the scoped copy.
- The 나 count leaves conversation rows out (QA TC-256: "each unread counted once").

So one notice shows in two lists, under two names, with two counts.

What Slack does (checked 2026-11-26 in Slack's help centre: "Introducing the new Activity view", "Get your work done
from the Activity view", "Use threads", "Customize the Slack mobile app"):
- **Activity** is one rail tab. It is a feed of events, one row per event. Its filters are Unreads, DMs, Mentions,
  Threads, Channels, Reactions, Invitations, Apps and Reminders, and there is no separate unread toggle.
- **Threads** is a different thing: a row at the top of Home that lists the conversations of the threads I am in, with
  unread ones first. Activity's Threads filter is the notices of those threads.
- **Badges:** Activity's icon carries a number that includes DMs and mentions. Channels in Home go bold. A DM therefore
  shows on the DMs tab and in Activity.
- **Phone:** the bottom tabs are Home · DMs · Activity. Threads is a tile at the top of Home.

## Scope

**Removed**
- The 대화 panel's "멘션·스레드" row (`rooms-activity`), on computers.
- The same row at the top of the phone's 대화 list.
- 활동's line "멘션·스레드는 대화에 있어요 ›" (`activity-panel-to-chats`).
- The scoped page `?in=chats`: `CHATS_ACTIVITY`, `activityInChats`, the `chats` branch of `pages/Activity.tsx`, and
  the "멘션·스레드" title in the phone's top bar.
- The 대화 mark's fallback dot for "only a mention or thread notice is unread". Those notices now count on 활동.

**Kept**
- The server and the API, unchanged. `only=rooms|notices` stays for older windows, and the new list asks without it.
- The phone page: tabs 전체 · DM · 멘션 · 스레드, Unreads, search, Mark all as read.
- The computer chips 트리나 and 요청, with today's rules for who sees 요청.
- The rows, how a notice opens, and how opening it reads it.
- Notification settings, pushes, e-mails and desktop notices. None of them link to `?in=chats`; they open the room or
  the notice itself.

**Moved**
- The 활동 panel lists every notice. The panel asks `GET /api/notifications` without `only` and counts `unreadCount`.
- The panel's chips become **전체 · DM · 멘션 · 스레드 · 트리나 · 요청**. They wrap to a second line when they do not
  fit, as they wrap today.
  - The first four use the shared tab rule `activityTabHas`, so the server marks the same rows read.
  - "Mark all as read" shows under 전체, DM, 멘션 and 스레드 (the server's tabs). It does not show under 트리나 or 요청:
    those chips are the client's own, so the server can't read them alone. That is today's rule, for 전체 only.
- **What DM holds.** The server lists a conversation row only for a mention or a reply in a thread I follow
  (`server/src/rooms/inbox.ts` `LISTED_SQL`). A plain DM message gets no row, as in Trina today. So DM is those rows
  of a direct or group chat. The chip stays because the owner brought the DMs tab back (DECISIONS "Activity: the DMs
  tab is back"), and the phone already has it. Its empty state says "Messages in DMs are in Chats" (`feed.dmsEmpty`)
  with the link to 대화.
  - Listing every DM message in Activity, as Slack does, is a server change. It would also flood the count, so it is
    out of scope (see Owner decisions 3).
- **A conversation row in the panel** is a `ListRow`:
  - Its icon slot holds the newest writer's photo at the slot's size: the people-list `face` box, initials when there
    is no photo, and the AI's mark for an AI answer.
  - Its name is who, grouped as the server sends it ("민준 외 2명"), then the message's first line, which carries its
    own @name. There is no second "@" in front of it: the first build drew "@@Olga". A screen reader hears "mention"
    on the unread dot. It takes two lines at most (`wrap`).
  - Its meta is where, in `bdi` (`#room › 스레드`, "다이렉트 메시지", a chat's title), and the time.
  - A chat-thread reply has the same parts. Other notices keep their bell, star or plug.
  - These are the parts the phone page shows (`roomRowText`), fitted to a panel row.
- **Opening a conversation row** opens its room or thread on the right, and 활동 stays lit (`noticeTarget`'s
  `rail: 'activity'` state), as in Slack. The row stays selected (`openNotice` matches the room and thread links).
- **Empty states:**
  - 전체: `notifications.empty`.
  - DM: `feed.dmsEmpty`.
  - 멘션, 스레드, 트리나 and 요청: `feed.emptyFiltered`.
  - Each keeps the "New messages are in Chats" link (`feed.newInChats`) while 대화 has unread rooms. It is the only
    pointer from an empty 활동 to plain unread messages, which are never notices.
- **Mark all as read** without `only` also moves my read place in each listed room and thread to its newest message,
  the same as the phone does today, so those rooms' 대화 marks drop as well. This is intended. Under 멘션 or 스레드, the
  count is read again after the mark, so the rail never shows 0 for what is left.

**Old links** (nothing 404s, each a `replace`):

| Link | Goes to |
|---|---|
| `/activity?in=chats` | `/activity` |
| `/activity?in=chats&tab=X` | `/activity?tab=X` |
| `/activity?tab=mentions\|threads\|dms` on a computer | Stays on `/activity`, with the 활동 panel opened on that chip. Today it bounced to 대화. |
| A `?in=chats` kept in this browser tab's rail memory or a phone tab stack (sessionStorage) | Dropped when read: its place is no longer 대화's. |

## Badges

| Where | Today | After |
|---|---|---|
| Rail 활동 (computer) | non-conversation notices | **every unread notice** (`unreadCount`), the panel's own number |
| Rail 대화 (computer), phone 대화 tab | unread conversations, else a dot for unread mention/thread notices | unread conversations only, no dot |
| Phone 나 tab, 나 › 활동 row | the app's own notices | **every unread notice**, the same number as the rail's 활동 |
| Settings › Notifications count | phone: notices; computer: everything | everything on both |

Only a mention, or a reply in a thread I follow, now counts in two places: on 대화 (its room, when the room counts it)
and on 활동/나 (its notice), as in Slack. A plain message, in a DM or anywhere else, is never a notice: it counts on
대화 alone. This supersedes "each unread counted once" (QA TC-256): with one Activity, the notice has one home and its
room keeps its own mark.

## Roles

- **Owner and admins:** 요청 as today.
- **Members:** 요청 only while an ask to open something of theirs is listed (today's rule).
- **Guests:**
  - They keep 활동, which every guest has. A guest with no 대화 place used to see their mentions only on a phone's

## Owner decisions (recommendations taken, the owner can overrule)

1. **The 대화 row: remove it, or turn it into "스레드" (the threads I'm in, as conversations)?** Recommendation:
   **remove it now.**
   - A Slack-style Threads list needs a new server list of the threads I follow: the root, the newest replies and an
     unread count per thread. Nothing like it exists; the only thread call today is one thread's page.
   - Activity's 스레드 chip already brings every new reply in a thread I follow. It's one tap from the rail, with the
     count.
   - A second list that starts out nearly empty goes against "lean UI".
   - If people ask for it, it comes back as its own plan: a 스레드 row in 대화 for that list, never a copy of Activity.
2. **Phone: Activity stays in 나, or gets its own bottom tab like Slack?** Recommendation: **it stays in 나, and the
   나 count includes everything.**
   - A sixth tab would break the five-slot bar (`docs/DECISIONS.md` "Phone tabs").
   - It is two taps, as the removed row was.
3. **Every DM message as a notice, as in Slack?** Not now. It needs a server change and would flood 활동's count. It
   gets its own plan only if the owner asks for it. DM stays a chip for the rows the server lists today.

## Risks

- **Double counts:** a mention or a followed thread reply shows on 대화 and on 활동. This is deliberate (Slack), and the
  decision says why.
- **The panel's width:** six chips in a 240–300 px panel take two lines. Check them in English and Spanish, the longest
  words.
- **Tests that pin `rooms-activity` or `?in=chats`:** about 12 e2e files and 6 unit files. They move to the new place;
  none are deleted without a replacement.
- No migration, no permission change, no server change.
