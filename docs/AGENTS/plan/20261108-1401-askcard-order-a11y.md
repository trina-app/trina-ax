# Room AI cards follow-up: reading order, keys, an ended turn, removed members, no chat id

- Date (UTC): 2026-11-08 14:01
- Branch: `fix/askcard-order-a11y`
- Status: done
- Where: trina-ax core (`web/src/components/chat/`, `web/src/store/`, `server/src/rooms/`, `shared/src/api/`). Why: the
  AI's confirmation cards and rooms are core (see docs/REPOSITORY-RULES.md)
- Version impact: patch. An accessibility fix and a smaller response of an endpoint added in the same unreleased
  version.

## Goal

Review follow-ups of #218 (room AI cards come back after a reload):

1. `ChoiceRow` (the three-button cards) put the main button last in the DOM and showed it on top on a phone with
   `flex-col-reverse`: on a phone the focus order ran bottom to top (WCAG 2.4.3). Its error line sat in the row, before
   the buttons in the DOM.
2. Its buttons were keyed by their label.
3. `loadAi`: a card whose turn ended between the read of the runs and the read of the cards was not described or tested.
4. `b-rooms-ai-cards` did not cover a removed member or a disabled account.
5. `GET /api/rooms/:id/ai/requests` answered each card's `chatId`, which the web does not use for a room.

## Scope

In:
- The main button first in the DOM: stacked on a phone in that order (main on top); `sm:flex-row-reverse` on a
  computer, so the row still reads [허용 안 함] [이 방에서는 항상 허용] [이번만 허용]. The error line after the buttons, in the
  DOM and on screen (under the row). The room's change card, the address card and the dev-environment card (all
  `ChoiceRow`). Unit and a11y tests assert the DOM order.
- Keys by index.
- `loadAi`: a comment and a web unit test: such a card is neither merged nor dropped, and goes with the turn's
  `turn.request.closed`.
- Server tests: a member removed from the room, the asker removed (their question stops, the card closes) and a
  disabled account get no cards.
- The room list answers `{ turnId, messageId, request }` (`RoomTurnRequest`), no `chatId`: a room session's chat is
  never listed or opened as a chat, and the room finds a card by its turn. The web keeps cards of rooms without a chat
  id (`OpenRequest.chatId` optional).

Out: the two-button card (one row on every screen, its DOM order is its visual order).

## Risks

On a computer the focus order now runs from the main button (right) to "no" (left): one DOM order cannot match both
layouts, and the phone, where the buttons stack, is where reading order and position must agree. No migration, no new
words.

## Tests

`bun run typecheck`, the AskCard and a11y web units, the Docker web unit suite, `b-rooms-ai-cards`, the room-ai-allow
e2e spec (and room-ai-cards, a11y).

## Result

Built as planned. `ChoiceRow` holds the server's order in the page (the phone's stack); a computer reverses the row.
The error line is a separate line after the row. `RoomTurnRequest` drops the chat id; the web store's `chatId` is
optional (`cardChats` skips cards without one). Tests: `ask-card-confirm` (page order, phone column, the error after the
buttons, the address and dev-environment cards), `design-contrast`, `room-ai-cards.test.ts` (the ended turn, no chat
id), `b-rooms-ai-cards` (7: a member taken out, the asker taken out, a disabled account), `a11y.spec.ts`,
`room-ai-allow.spec.ts` and `room-ai-cards.spec.ts` (page order, Tab top to bottom on a phone).

Not changed: the skill share card and the welcome steps use `max-sm:order-*` for their stacked buttons, which has the
same phone reading-order issue; a follow-up can move them to the rule now in docs/DESIGN-SYSTEM.md.
