# Microsoft 365 connector: Outlook mail, Calendar, OneDrive/SharePoint files, Teams chat

- Date (UTC): 2026-11-25 04:20
- Branch: `feat/m365-connector`
- Status: done
- Where: server/src/integrations/microsoft/ (new), connections/service.ts (sign-in and transport hooks),
  shared/src/service-catalog.ts, web Discover entry, docs. Why: a listed connector that signs in through an app the
  server holds is the GitHub pattern already in the core (docs/REPOSITORY-RULES.md: connectors go in the core)
- Version impact: minor: a new connector people can use (new feature, nothing changes for existing connections)

## Goal

A person (or an admin, for the team) presses Connect on "Microsoft 365" in Settings › Connectors (or the chat's
connect card), signs in with their Microsoft work or school account, and the AI can search and read Outlook mail,
write drafts and send mail, list and create calendar events, find, read and upload OneDrive or SharePoint files, and
list Teams chats, read them and send a message. Microsoft 365 is the most used connector in Claude's directory that
Trina lacks (owner's ask, 2026-11-25).

## Approach

Microsoft has no remote MCP server a third-party app can sign in to (the Agent 365 / Work IQ servers need a Microsoft
365 Copilot licence, admin enablement and Microsoft's own client; checked 2026-11-25). So the tools are ours, over
Microsoft Graph, in the shape of the Google connectors but with the least new machinery:

- A **listed service** like GitHub: `microsoft365` in `shared/src/service-catalog.ts` with `serverApp: 'microsoft'`
  and the reserved address `https://microsoft-365.invalid/mcp` (never resolves). Every connection rule is the generic
  one: personal or team, the write card and Always allow, per-tool switches, sealed tokens and refresh, scheduled-run
  rules, the audit, secrets hidden, the chat's connect card.
- **Sign-in** through the Microsoft app the server holds (`MYCEL_MICROSOFT_APP_FILE`, else
  `<secrets>/integrations/microsoft/app.json`: `{ clientId, clientSecret, tenant? }`, read like the GitHub App file),
  at Microsoft's fixed addresses (`https://login.microsoftonline.com/<tenant, default common>/oauth2/v2.0/...`),
  PKCE, fixed delegated scopes with `offline_access`, no resource indicator (Entra v2 refuses one). Refresh with the
  app as it is now; Microsoft's rotated refresh token is kept (generic keepTokens). A person may still use their own
  Entra app instead (the generic "own app" fields).
- **Return address per install type:** the desktop app (Windows, Mac, Linux) signs in through its one-time
  `http://127.0.0.1:<port>/callback` (RFC 8252; Entra ignores the port of a loopback address), so it works against any
  server, hosted or self-installed; the web uses the team's `https://<host>/api/integrations/oauth/callback` (hosted
  teams: one wildcard entry for the team domain, only for a work/school-only Entra app); a server opened at
  `http://localhost` or `127.0.0.1` uses that address.
- **Transport**: the connection's MCP client sends its requests to an MCP server inside this process
  (`microsoft/mcp-server.ts`), which reads the bearer token and calls `https://graph.microsoft.com/v1.0` through
  `net.ts` (public https only). Graph's 401 is the MCP answer's 401 (refresh once, then "sign in again", the existing
  refusal mapping); other Graph errors are a tool error with Microsoft's words, cleaned (refusal.ts cleanSaid).
- **Hosted teams** get the app file through a new tenant command `microsoft-app-set` (mirrors `github-app-set`).

## Scope

In: the catalog entry, app file, sign-in hooks, in-process Graph tools (mail search/read/draft/send-draft/send,
calendar list/create, files search/read/upload, Teams list chats/read/send), the tenant command, Discover logo and
descriptions in six languages, docs (CONNECTIONS.md, INTEGRATIONS.md), unit tests with Graph faked.
Out: the account.trina.app broker for Microsoft (only needed for personal Microsoft accounts or to drop the hosted
wildcard: a trina-cloud change), attachments of mail, Teams channels, a live mailbox test (the test tenant has no
licence now), publisher verification.

## Risks

- No migration (a listed service is an ordinary connection row).
- Security: the client secret stays in the server's private file and goes only to Microsoft's token address; tokens go
  only to graph.microsoft.com (and a file's pre-signed download address Graph names on its own hosts); the reserved
  address never resolves, so an older build sends nothing anywhere.
- Entra: tenants that allow user consent only for verified publishers need an admin's consent until the app is
  publisher-verified.
- Six languages for the Discover description; the desktop path needs `http://127.0.0.1/callback` on the Entra app.

## Result

Built as planned: `server/src/integrations/microsoft/` (app.ts, graph.ts, mcp-server.ts with 13 tools), the
`serverApp: 'microsoft'` hooks in connections/service.ts (fixed Microsoft addresses and scopes, no resource, the
desktop app's 127.0.0.1 return address, the in-process transport, refresh with the current secret), the Discover entry
(logo, six languages, "Not set up yet"), the tenant command `microsoft-app-set` (contract, vectors, mycel-ctl, Go
test), docs (INTEGRATIONS.md "Microsoft 365", CONNECTIONS.md) and `tests/unit/c-integrations-microsoft.test.ts`.
Differs from the plan: none in scope. A sign-in made with another client ID keeps its stored client until Microsoft
refuses it (as GitHub), not "ended at once". Not tested live: the test tenant has no Microsoft 365 licence (no
mailbox); the registered app's client ID and secret were checked against Microsoft's token address only.
