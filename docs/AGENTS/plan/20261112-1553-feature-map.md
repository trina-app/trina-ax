# Feature map: which features the tests reach

- Date (UTC): 2026-11-12 15:53
- Branch: `feat/feature-map`
- Status: in progress
- Where: trina-ax `docs/features.ts`, `scripts/features/`, `web/test/mock/server.ts`, `web/test/e2e/`. Why: the map is
  built from the code that is in this repo (the API contract and the web app's routes), so it belongs next to it.
- Version impact: none (developer tooling and tests; no product change)

## Goal

The owner wants to see which features are tested and which are not, without a hand-kept list that goes stale. Units
(API endpoints, web screens) are read from the code; only their grouping into ~100 named features is kept by hand, and a
check fails when a new endpoint or screen belongs to no feature. The e2e suite records which endpoints and screens each
test reached, so "covered" is measured, not typed.

## Scope

In:
- `docs/features.ts`: the features (stable IDs, plain names, area, the endpoints and screens each one claims, and
  hand-listed desktop/phone features with no endpoint or screen).
- `scripts/features/`: reads the API registry, `web/src/App.tsx` routes, Settings sections and Admin pages; writes
  `docs/features.generated.json`; `bun run features:check` fails on an unclaimed endpoint or screen, a pattern that claims
  nothing, a duplicate ID, a stale generated file, or an e2e spec that does not use the recording `test`.
- Mock server: records the endpoint of every API request per test. A Playwright fixture (`web/test/e2e/fixtures.ts`)
  names the running test and records the addresses the pages visited; the run writes
  `web/test-results/feature-coverage.json`.
- CI: `features:check` in the static job; a separate workflow runs the e2e suite on dev and uploads the coverage file.
- `docs/FEATURES.md`: how to add a mapping.

Out: the Google Sheet "Features" tab and the QA tab's Feature column (a script run on a Mac with the sheet's sign-in,
after this merges), unit-test coverage per feature.

## Steps

1. Generator + check + unit tests.
2. Draft `docs/features.ts` from the endpoint summaries and routes.
3. Mock server recorder, fixture, spec imports, coverage file.
4. CI wiring, docs page, changelog fragment.

## Risks

- Every e2e spec's import line changes (`test` from `./fixtures`): other open PRs touching a spec's first lines may
  conflict; a new spec that imports from `@playwright/test` fails `features:check` with the fix in the message.
- The e2e workflow is new in CI and not required; it must not slow down pull requests (runs on dev pushes only).
