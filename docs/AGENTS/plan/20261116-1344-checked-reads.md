# File reads use the file that was checked

- Version impact: patch (a fix, no API or migration)

## Goal

#1123 made downloads read the file their permission check saw (`openChecked(abs, seen)` in `team-files/place.ts`). The
other file reads still open the checked path again by name: the AI's read tools, the file screen's text view and the
other places that read a team file's content. A personal folder is also written by that person's dev environment runs,
so a folder on the way can change between the check and the open. Every read of a checked team file must read the very
file that was checked; a link placed under a personal folder is never followed.

## Scope

In:

- `readRegular(abs, max, seen?)` and `sha256Regular(abs, seen?)`: with the check's `lstat`, open through
  `openChecked(abs, seen)` and read only from that descriptor; after the check every failure is the one refusal ("path
  changed while opening"). What the check itself saw (a folder, a link, a hard link) answers as before.
- The file screen's `content`: one checked open; the hash and the text come from that descriptor.
- `moveToTrash` (AI delete): the copy kept in the trash is read from the checked file.
- Every caller that has the check's `lstat` passes it; callers that read server-owned folders (uploads, work folders,
  caches) stay as they are. Each caller and what it does is listed under Result.
- A changelog fragment.

Out: what any caller may read does not change. `files/search-admission.ts` (the search index's own reader) is noted as
a follow-up, not changed here.

None. No rule changes: links were refused already; reads now keep to it at every step.

## Risks

- A file replaced by a normal save between the check and the open is refused once; the next read works.
- `openChecked` compares the open file's own path with the checked path; callers pass `seen` only where `abs` is the
  checked path (`authorize`: the team folder's real path plus the names on disk).
