# File reads use the file that was checked

- Date (UTC): 2026-11-16 13:44
- Branch: `fix/checked-reads` (on `fix/download-checked-descriptor`, PR #1123)
- Status: done
- Where: trina-ax core: `server/src/files/store.ts` (`readRegular`, `sha256Regular`, `moveToTrash`),
  `server/src/team-files/service.ts` (the file screen's `content`) and the callers of `readRegular`. Why: file
  permissions and file reads are core (docs/REPOSITORY-RULES.md).
- Version impact: patch (a fix, no API or migration)

## Goal

#1123 made downloads read the file their permission check saw (`openChecked(abs, seen)` in `team-files/place.ts`). The
other file reads still open the checked path again by name: the AI's read tools, the file screen's text view and the
other places that read a team file's content. A personal folder is also written by that person's dev environment runs,
so a folder on the way can change between the check and the open. Every read of a checked team file must read the very
file that was checked; a link placed under a personal folder is never followed.

## Scope

In:

- `readRegular(abs, max, seen?)` and `sha256Regular(abs, seen?)`: with the check's `lstat`, open through
  `openChecked(abs, seen)` and read only from that descriptor; after the check every failure is the one refusal ("path
  changed while opening"). What the check itself saw (a folder, a link, a hard link) answers as before.
- The file screen's `content`: one checked open; the hash and the text come from that descriptor.
- `moveToTrash` (AI delete): the copy kept in the trash is read from the checked file.
- Every caller that has the check's `lstat` passes it; callers that read server-owned folders (uploads, work folders,
  caches) stay as they are. Each caller and what it does is listed under Result.
- A changelog fragment.

Out: what any caller may read does not change. `files/search-admission.ts` (the search index's own reader) is noted as
a follow-up, not changed here.

## Steps

1. Tests first (`tests/unit/checked-reads.test.ts`): a folder on the way swapped for a link right before the open, for
   the AI read tool and the file screen; run on #1123's head and note the result.
2. `readRegular` / `sha256Regular` with `seen`; `content`; `moveToTrash`.
3. Callers.
4. Checks on macOS and in the `oven/bun:1.3.12-debian` image.

## Decisions

None. No rule changes: links were refused already; reads now keep to it at every step.

## Risks

- A file replaced by a normal save between the check and the open is refused once; the next read works.
- `openChecked` compares the open file's own path with the checked path; callers pass `seen` only where `abs` is the
  checked path (`authorize`: the team folder's real path plus the names on disk).

## Tests

`bun run typecheck`; under Bun 1.3.12 the new test, `download-checked-descriptor`, `c-files`, `c-file-shares`, the AI
read tool tests and the store/team-files tests touched, on this Mac and in `oven/bun:1.3.12-debian`.

## Result

Built as planned.

- `readRegular(abs, max, seen)` and `sha256Regular(abs, seen)`: with `seen`, what the check saw answers as before (a
  folder, a link, a hard link), then `openChecked(abs, seen)`; the bytes come from that one descriptor. Without `seen`,
  as before.
- The file screen's text view (`team-files/service.ts content`) opens once with `openChecked(r.abs, r.st)`; its hash
  and its text come from that descriptor (the hash cache is unchanged).
- `moveToTrash` takes the check's `lstat` (AI delete): the copy kept in the trash is of the checked file.
- Callers given the check's `lstat` (from `authorize`): the AI read tool's text, images, PDFs and media sources
  (`files/service.ts` readText, boundSource), `textNow`, AI write/edit (current bytes before saving), the file screen's
  save, `edit_hwp`, `stamp_pdf`, the PDF tools, `make_file` (sources, `.hwpx` template, HTML print and its pictures, the
  file it replaces), the team's rule files in the prompt, skill files (listing and checks), the change card's current
  bytes (`chat/turn.ts`), promo video and intro deck sources and pictures, safe operations' source, the company profile,
  skill packs, file organizing, the old-file key scan. Given a fresh `lstat` of a checked path, right before the open:
  the own-file hash of `chat/turn.ts` and `chat/schedule-cover.ts`, the skill change kind (`skills/changes.ts`), a
  skill folder's files on a card (`skills/folder-actions.ts`).
- Unchanged, and why: chat and room uploads, converter output, the search cache's own files (server-owned folders);
  `skillEntriesOnDisk`, `folder-actions` `bytesOf` / `looksText` and `settleAside` (they read only a skill's name, a yes
  or no, or a hash to compare, and nothing of the file leaves); `quarantine.hasFile` (a hash that can only add a
  refusal); `freshChanges` (old bytes of a moved skill file, re-checked by the card's `recheck` before the move);
  `hashFile` in `replacing` (hash only, the file's identity is compared again after); `copyMedia` (compares identity
  before and after); `currentHash` (no callers).
- Follow-up, not in this change: `files/search-admission.ts` (the search index's reader) compares the open file with
  a fresh `lstat` of the path, not with the open file's own path.
- Tests: `tests/unit/checked-reads.test.ts`, 6 of 11 fail on #1123's head (the swap and save cases), 11/11 after.
